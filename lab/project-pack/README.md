# project-pack — プロジェクトの持ち出し / 取り込み

プロジェクトを **1 個のファイル**にまとめて、別の端末で開けるようにするための試作。

いまの本体（`src/engine/project-file.ts`）は**参照素材の在り処だけ**を畳んでいて、
取り込んだ素材は「運べません」と名前を出して落としている。
実体を入れるかどうかは決まっていなかったので、**入れたらどうなるかを測って決める**のが今回。

触る画面は無い。出口はコマンドだけ。

```
npm run lab:test               # 決め方・並べ方・壊れたファイルの検算（ブラウザ不要・数秒）
npm run lab:pack               # 大きさ・時間・メモリを測る
LAB_PACK_WALL=1 npm run lab:pack   # base64 の壁に実際にぶつける（400MB 確保する）
```

## 何を運ぶかは 3 つに分かれる（`src/plan.ts`）

| | どうする | なぜ |
| --- | --- | --- |
| `ref` | 在り処（`src`）だけ入れる | 実体は相手にも見えている。二重に運ぶ意味が無い |
| `embed` | 実体をファイルに入れる | 相手の端末には無い。入れるしか渡す道が無い |
| `dropped` | 名前だけ控える | 実体がもう手元に無い／上限を超えた |

**参照素材の実体は、手元にあっても埋めない。** 開いた側は `src` を先に見るので、
埋めたぶんは使われずファイルだけが太る。

決め方の段は**実体を 1 バイトも読まない**（`BodySource.size` しか呼ばない）。
`Blob.size` はタダで `Blob.arrayBuffer()` は高いという差を、型のうえで分けてある。
おかげで「この構成なら何 MB になるか」を、書き出す前に画面へ出せる。

## 測って分かったこと（2026-09-28・node v22・交互 5 巡の中央値）

### 1. 大きさ — base64 はきれいに 1.333 倍

| 構成 | 実体 MB | 参照だけ | JSON MB | 二進 MB | JSON/二進 |
| --- | ---: | ---: | ---: | ---: | ---: |
| 効果音だけ（30KB × 40） | 1.17 | 1763 B | 1.57 | 1.18 | 1.330 倍 |
| 短い動画 1 本 | 12.00 | 185 B | 16.00 | 12.00 | 1.333 倍 |
| 動画 8 本 | 96.00 | 456 B | 128.00 | 96.00 | **1.333 倍** |
| 参照 6 本＋取り込み 2 本 | 8.03 | 1478 B | 10.71 | 8.03 | 1.333 倍 |

「参照だけ」はいまの本体の形。**実体を運ばないので、素材が何 MB あってもファイルは数百バイト。**
実体を入れると、当然そのぶんそのまま重くなる。ここは驚きが無い。

見出しは 1 素材あたり **約 243 バイト**（サムネイルを入れていない状態）。

### 2. 時間 — 二進は「組む」がほぼ 0。仕事は「書く」に残る

| 構成 | JSON 組む | 二進 組む | JSON 書く | 二進 書く | JSON 計 | 二進 計 |
| --- | ---: | ---: | ---: | ---: | ---: | ---: |
| 効果音だけ | 8.1 | 0.2 | 2.4 | **6.0** | 10.5 | 6.2 |
| 短い動画 1 本 | 125.8 | 0.1 | 25.0 | 4.9 | 150.8 | 5.1 |
| 動画 8 本 | 1911.4 | 0.2 | 378.1 | 55.4 | **2289.4** | **55.6** |
| 参照 6 本＋取り込み 2 本 | 65.6 | 0.2 | 12.6 | 3.3 | 78.1 | 3.4 |

単位 ms。**「組む」だけを並べると二進が不当に有利に見える**（写しを作らないので 0 に近い）。
書く時間まで足して初めて比べられるので、そこまで測った。96MB で **2.29 秒 対 0.056 秒**。

**1 か所だけ二進が負ける。** 「効果音だけ」の書く段が 6.0ms 対 2.4ms。
実体が 40 個あると `write()` を 40 回呼ぶからで、1 回あたりの手間が中身より重くなる。
数 ms なので放っておくが、素材が数百個あるなら小さい実体はまとめて書く形が要る。

### 3. メモリ — ここが本当の理由。JSON は実体の 6.7 倍を積む

| 構成 | 実体 MB | 素材だけ | JSON MB | 二進 MB | JSON 上乗せ |
| --- | ---: | ---: | ---: | ---: | ---: |
| 効果音だけ | 1.17 | 4.88 | 15.50 | 4.75 | 9.1 倍 |
| 短い動画 1 本 | 12.00 | 16.00 | 95.70 | 15.75 | 6.6 倍 |
| 動画 8 本 | 96.00 | 100.75 | **746.35** | 100.63 | **6.7 倍** |
| 参照 6 本＋取り込み 2 本 | 8.03 | 12.00 | 66.19 | 11.50 | 6.7 倍 |

**96MB の素材を入れるのに 746MB の山が立つ。** 内訳は、base64 の文字列（実体の 1.33 倍）と
`JSON.stringify` の結果（同じく 1.33 倍）を**同時に**抱え、そこへ写しが乗る。
二進の側は「素材を用意しただけ」と同じ。実体への参照を並べるだけなので、上乗せが無い。

ブラウザならもっと差が開く。二進の側は実体が `Blob` のままで、
`new Blob([前置き, ...実体の Blob])` を作っても**中身はどこにも起きない**。

### 4. 開くとき — 実体 1 つ取り出すのに 31 倍

96MB・8 本のファイルから 6 本目だけを取り出す:

| やること | ms | 読んだ MB |
| --- | ---: | ---: |
| 二進：見出しを読む | 0.95 | 0.00（2KB） |
| 二進：実体 1 つを切り出す | 11.26 | 12.00 |
| JSON：全体を `JSON.parse` する | 378.19 | 128.00 |
| JSON：base64 を 1 つ戻す | 6.36 | — |

**二進 12.2ms（12MB 読む）／ JSON 384.6ms（128MB 読む）＝ 31 倍。**

差は速さの話ではなく**届き方**の話。JSON では、実体 1 つに手を伸ばすためにも
ファイルぜんたいを 1 本の文字列にして `JSON.parse` を通さないといけない
（本体の `openProject` も `await file.text()` でそうしている）。
二進なら `blob.slice(offset, offset + length)` でその実体だけが手に入り、
`URL.createObjectURL` にそのまま渡せる。

### 5. JSON に埋める形には天井がある

```
文字列の上限            536,870,888 文字   （V8 の String::kMaxLength）
base64 の太り方          1.3333 倍
入れられる実体の合計     384.00MB
```

実際にぶつけると:

```
380MB → base64 できた（531,278,508 文字）
420MB → Cannot create a string longer than 0x1fffffe8 characters
```

**1 本ごとではなく合計。** `JSON.stringify` はファイルぜんたいを 1 本の文字列にするので、
12MB の動画なら 31 本、100MB なら 3 本で天井に当たる。

ただし **この天井より先にメモリで死ぬ**。上の表のとおり実体の 6.7 倍を積むので、
384MB ぶんを入れようとすると山は 2.5GB を越える。スマホでは 96MB でも危ない。
**「太るから駄目」ではなく「載らないから駄目」。**

測ったのは Node の V8。Chrome も同じ V8 なので同じ数字になる。
**Safari（JavaScriptCore）は測れていない**ので、上限の値は違うかもしれない。
ただし「1 本の文字列に全部を通す」という形そのものが壁を作るところは変わらない。

## 並べ方（`src/container.ts`）

```
[0,8)        "VIVIDPK1"           目印
[8,12)       uint32LE             見出しの**バイト**長 H
[12,12+H)    見出し（UTF-8 の JSON）
[12+H, …)    実体。見出しの bodies の順に、隙間なく並べる
```

決めるのに引っかかった所が 3 つある。

**位置は「実体域の先頭から」の相対で持つ。** ファイル先頭からの絶対位置で書くと、
位置の桁が伸びたぶん見出しが伸びて、その伸びたぶん位置がずれる（不動点を解く話になる）。
実体域の先頭を 0 にすれば、見出しの長さと位置が切り離せて 1 回で決まる。

**見出しの長さは「文字数」ではなく「バイト数」。** 素材名に日本語が入ると
JSON の文字数と UTF-8 のバイト数がずれる（測ったら 387 文字 = 423 バイト）。
文字数で書くと見出しの終わりが手前にずれて、実体の頭が見出しに食われる。

**詰める順は id の昇順。** `usedMediaIds` が返す順はクリップの並びに依るので、
そのまま詰めるとクリップを 1 つ動かしただけで実体の位置が全部ずれる。
それでは「同じプロジェクトを 2 回書き出したら同じファイルになる」が崩れて、差分も取れない。

## 壊れを見つける値（ハッシュ）は入れない

速さは理由にならない。96MB の sha256 は **79ms（1213MB/s）**で、書く時間より軽い。

入れない理由は**ブラウザに流しながら計算する口が無い**こと。
`crypto.subtle.digest` は `BufferSource` を丸ごと受け取る形しか無く、少しずつ食わせられない。
つまりハッシュを入れると、**「実体をメモリに乗せない」という二進の入れ物のいちばんの利点が消える**。
96MB を渡すために 96MB 起こすなら、JSON に埋めるのと同じ穴に落ちる。

入れるなら素材ごとに分けて、**開くときではなく「確かめる」ときだけ**計算する形になる。
それは別の回の話。

## 壊れたファイルの扱い

**1 つ壊れていても全部を捨てない。** 本体の `parseProjectFile` も形の合わない素材だけを落としている。
ただし黙って落とすと「開いたら一部が黒い」になるので、名前を `outOfRange` に出す
（本体の `localOnly` と同じ扱い。「この 3 つは運べません」の方が扱いやすい）。

断るのは、ファイルとして読み進められないときだけ:

| | どうする |
| --- | --- |
| 短すぎる / 目印が違う | 断る |
| 見出しがファイルの外へはみ出す（途中で切れた） | 断る |
| 見出しが JSON でない | 断る |
| 新しい版 | 断る（「アプリを新しくしてから」と言う） |
| トラックが無い | 断る |
| 実体の位置が範囲外・負・小数 | **その素材だけ**落として名前を出す |

**見ていないもの**: 実体の中身が本当にその素材かどうか。長さが合っていれば通る。
上のとおりハッシュを入れていないので、ここは開いてから気づくしかない。

## 本体へ持っていくときに要るもの

`src/plan.ts` と `src/container.ts` だけ。どちらも DOM にも Node にも依存していない
（`TextEncoder` / `DataView` しか使っていない）。`json-pack.ts` は比べるために書いたもので、
測り終わったので持っていかない。

本体側で足すことになるのは:

- `MediaAsset` に `mime` を持つ（埋めた実体を `new Blob([bytes], { type })` で戻すのに要る）。
  いまは `File.type` を捨てているので、`media.ts` の `add()` で拾う必要がある。
- `mediaRegistry.adopt()` に「実体つきで迎え入れる」口。
  いまの `adopt` は参照素材（`src` あり）しか受けない。
- 書き出しは `saveBlob(new Blob([layout.prefix, ...実体の Blob]))`。
  `JSON.stringify` を通さないので、素材が何 GB あっても文字列の壁に当たらない。
- 拡張子。いまは `.vivid.json`。中身が JSON でなくなるので `.vividpack` のような別の名前が要る
  （`.json` のまま二進を入れるのがいちばん良くない）。

## 積み残し

- **サムネイルを見出しから追い出すか。** 見出しは開くとき必ず全部読む。
  いまは 1 素材 243 バイトだが、`thumbnail` の data URL を入れると 1 素材 10〜20KB になり、
  素材 1000 個で見出しだけで 20MB。実体と同じく後ろへ回すのが素直だが、
  **そうすると「一覧を出すのに実体域を読む」**ことになるので、測ってから決める。
- **小さい実体をまとめて書く。** 上の 2 の 1 か所だけ二進が負けたところ。
- **Safari で文字列の上限を測っていない。** 二進を選んだので効かないが、数字としては空いている。
- **実体の中身が合っているかを見る手が無い。** ハッシュの置き所（素材ごと・確かめるときだけ）。
- **画面が無い。** 本体へ入れるときに `SettingsPage` の保存／開くへ繋ぐ話になるので、
  試作の側で画面を作るより本体へ持っていく回のほうが早い。
