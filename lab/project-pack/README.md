# project-pack — プロジェクトの持ち出し / 取り込み

プロジェクトを **1 個のファイル**にまとめて、別の端末で開けるようにするための試作。

いまの本体（`src/engine/project-file.ts`）は**参照素材の在り処だけ**を畳んでいて、
取り込んだ素材は「運べません」と名前を出して落としている。
実体を入れるかどうかは決まっていなかったので、**入れたらどうなるかを測って決める**のが今回。

触る画面は無い。出口はコマンドだけ。

```
npm run lab:test               # 決め方・並べ方・壊れたファイルの検算（ブラウザ不要・数秒）
npm run lab:pack               # 大きさ・時間・メモリを測る
LAB_PACK_WALL=1 npm run lab:pack   # base64 の壁に実際にぶつける（400MB 確保する）
npm run lab:pack:thumbs        # サムネイルの置き所を 3 通り測る
npm run lab:pack:thumbsize     # 本物のサムネイルが何バイトかを焼いて測る（ブラウザが要る）
npm run lab:pack:digest        # 壊れを見つける値（ハッシュ）の費用と置き所
npm run lab:pack:edge          # そのハッシュを「端だけ」で取る形（何を見落とすか）
npm run lab:pack:width         # その端の幅を素材の大きさで変えるか（＝変えない。散らす）
```

## 何を運ぶかは 3 つに分かれる（`src/plan.ts`）

| | どうする | なぜ |
| --- | --- | --- |
| `ref` | 在り処（`src`）だけ入れる | 実体は相手にも見えている。二重に運ぶ意味が無い |
| `embed` | 実体をファイルに入れる | 相手の端末には無い。入れるしか渡す道が無い |
| `dropped` | 名前だけ控える | 実体がもう手元に無い／上限を超えた |

**参照素材の実体は、手元にあっても埋めない。** 開いた側は `src` を先に見るので、
埋めたぶんは使われずファイルだけが太る。

決め方の段は**実体を 1 バイトも読まない**（`BodySource.size` しか呼ばない）。
`Blob.size` はタダで `Blob.arrayBuffer()` は高いという差を、型のうえで分けてある。
おかげで「この構成なら何 MB になるか」を、書き出す前に画面へ出せる。

## 測って分かったこと（2026-09-28・node v22・交互 5 巡の中央値）

### 1. 大きさ — base64 はきれいに 1.333 倍

| 構成 | 実体 MB | 参照だけ | JSON MB | 二進 MB | JSON/二進 |
| --- | ---: | ---: | ---: | ---: | ---: |
| 効果音だけ（30KB × 40） | 1.17 | 1763 B | 1.57 | 1.18 | 1.330 倍 |
| 短い動画 1 本 | 12.00 | 185 B | 16.00 | 12.00 | 1.333 倍 |
| 動画 8 本 | 96.00 | 456 B | 128.00 | 96.00 | **1.333 倍** |
| 参照 6 本＋取り込み 2 本 | 8.03 | 1478 B | 10.71 | 8.03 | 1.333 倍 |

「参照だけ」はいまの本体の形。**実体を運ばないので、素材が何 MB あってもファイルは数百バイト。**
実体を入れると、当然そのぶんそのまま重くなる。ここは驚きが無い。

見出しは 1 素材あたり **約 245 バイト**（サムネイルは見出しに入れていない。理由は下の 6）。

### 2. 時間 — 二進は「組む」がほぼ 0。仕事は「書く」に残る

| 構成 | JSON 組む | 二進 組む | JSON 書く | 二進 書く | JSON 計 | 二進 計 |
| --- | ---: | ---: | ---: | ---: | ---: | ---: |
| 効果音だけ | 8.1 | 0.2 | 2.4 | **6.0** | 10.5 | 6.2 |
| 短い動画 1 本 | 125.8 | 0.1 | 25.0 | 4.9 | 150.8 | 5.1 |
| 動画 8 本 | 1911.4 | 0.2 | 378.1 | 55.4 | **2289.4** | **55.6** |
| 参照 6 本＋取り込み 2 本 | 65.6 | 0.2 | 12.6 | 3.3 | 78.1 | 3.4 |

単位 ms。**「組む」だけを並べると二進が不当に有利に見える**（写しを作らないので 0 に近い）。
書く時間まで足して初めて比べられるので、そこまで測った。96MB で **2.29 秒 対 0.056 秒**。

**1 か所だけ二進が負ける。** 「効果音だけ」の書く段が 6.0ms 対 2.4ms。
実体が 40 個あると `write()` を 40 回呼ぶからで、1 回あたりの手間が中身より重くなる。
数 ms なので放っておくが、素材が数百個あるなら小さい実体はまとめて書く形が要る。

### 3. メモリ — ここが本当の理由。JSON は実体の 6.7 倍を積む

| 構成 | 実体 MB | 素材だけ | JSON MB | 二進 MB | JSON 上乗せ |
| --- | ---: | ---: | ---: | ---: | ---: |
| 効果音だけ | 1.17 | 4.88 | 15.50 | 4.75 | 9.1 倍 |
| 短い動画 1 本 | 12.00 | 16.00 | 95.70 | 15.75 | 6.6 倍 |
| 動画 8 本 | 96.00 | 100.75 | **746.35** | 100.63 | **6.7 倍** |
| 参照 6 本＋取り込み 2 本 | 8.03 | 12.00 | 66.19 | 11.50 | 6.7 倍 |

**96MB の素材を入れるのに 746MB の山が立つ。** 内訳は、base64 の文字列（実体の 1.33 倍）と
`JSON.stringify` の結果（同じく 1.33 倍）を**同時に**抱え、そこへ写しが乗る。
二進の側は「素材を用意しただけ」と同じ。実体への参照を並べるだけなので、上乗せが無い。

ブラウザならもっと差が開く。二進の側は実体が `Blob` のままで、
`new Blob([前置き, ...実体の Blob])` を作っても**中身はどこにも起きない**。

### 4. 開くとき — 実体 1 つ取り出すのに 31 倍

96MB・8 本のファイルから 6 本目だけを取り出す:

| やること | ms | 読んだ MB |
| --- | ---: | ---: |
| 二進：見出しを読む | 0.95 | 0.00（2KB） |
| 二進：実体 1 つを切り出す | 11.26 | 12.00 |
| JSON：全体を `JSON.parse` する | 378.19 | 128.00 |
| JSON：base64 を 1 つ戻す | 6.36 | — |

**二進 12.2ms（12MB 読む）／ JSON 384.6ms（128MB 読む）＝ 31 倍。**

差は速さの話ではなく**届き方**の話。JSON では、実体 1 つに手を伸ばすためにも
ファイルぜんたいを 1 本の文字列にして `JSON.parse` を通さないといけない
（本体の `openProject` も `await file.text()` でそうしている）。
二進なら `blob.slice(offset, offset + length)` でその実体だけが手に入り、
`URL.createObjectURL` にそのまま渡せる。

### 5. JSON に埋める形には天井がある

```
文字列の上限            536,870,888 文字   （V8 の String::kMaxLength）
base64 の太り方          1.3333 倍
入れられる実体の合計     384.00MB
```

実際にぶつけると:

```
380MB → base64 できた（531,278,508 文字）
420MB → Cannot create a string longer than 0x1fffffe8 characters
```

**1 本ごとではなく合計。** `JSON.stringify` はファイルぜんたいを 1 本の文字列にするので、
12MB の動画なら 31 本、100MB なら 3 本で天井に当たる。

ただし **この天井より先にメモリで死ぬ**。上の表のとおり実体の 6.7 倍を積むので、
384MB ぶんを入れようとすると山は 2.5GB を越える。スマホでは 96MB でも危ない。
**「太るから駄目」ではなく「載らないから駄目」。**

測ったのは Node の V8。Chrome も同じ V8 なので同じ数字になる。
**Safari（JavaScriptCore）は測れていない**ので、上限の値は違うかもしれない。
ただし「1 本の文字列に全部を通す」という形そのものが壁を作るところは変わらない。

## 6. サムネイルの置き所（2026-09-28・2 回目）

見出しは**開くとき必ず全部読む**。素材の覚え書きだけなら 1 素材 245 バイトだが、
`MediaAsset.thumbnail` は `data:image/jpeg;base64,…` の**文字列**なので、そこに入れると桁が変わる。
9/28（1 回目）の積み残しは「1 素材 10〜20KB」と書いたが、**それは測った数字ではなかった。**

### 6.1 本物のサムネイルは 2.3〜6.4KB（当て推量の 2〜4 分の 1）

本体（`src/engine/media.ts` の `snapshot()`）と同じ規則——**長辺 240・JPEG 品質 0.7**——で
実寸（1920×1080 / 1080×1920）から焼いたもの（`npm run lab:pack:thumbsize`）:

| 素材 | 横型 生 B | 横型 data URL | 縦型 data URL |
| --- | ---: | ---: | ---: |
| whip-still（平らな面） | 2884 | 3868 | 3498 |
| whip-grain（粒） | 2963 | 3975 | 3570 |
| whip-captions（文字帯） | 4012 | 5372 | 5147 |
| cuts-plain（場面が多い） | 4675 | 6258 | 6007 |
| dark-noise（暗い） | 1781 | 2399 | 2456 |
| handheld（揺れ＋粒） | 4914 | 6576 | 6182 |

**中央値 5.0KB / 幅 2.3〜6.4KB**（12 通り）。data URL ÷ 生バイトは 1.338〜1.347 で、
base64 の 4/3 に `data:image/jpeg;base64,` の 23 文字が乗った形。
合成の素材は本物の映像より滑らかなので、**ここの数字は本物より小さめに出る**（下限として読む）。

**それでも結論は動かない。** 1 素材 245 バイトの覚え書きに対して 5KB は **20 倍**で、
素材 1000 個なら見出しだけで 5〜6.5MB。当て推量が 3 倍外れていても、答える向きは同じだった。

### 6.2 「後ろへ回す」には 2 通りあって、答えが逆になる

| | どこへ | 一覧を出すのに |
| --- | --- | --- |
| `inline` | 見出しの中（元の形） | 見出しを読めば済む（そのぶん見出しが太る） |
| `section` | 見出しと実体の間に**まとめて** | その一続きを **1 回**読む |
| `scattered` | 実体と同じ域へ、素材ごとに実体の後ろ | **素材の数だけ**読む |

素材 1000 個・実体 64KB ずつ（`npm run lab:pack:thumbs`）:

| 置き所 | 全体 MB | 見出し KB | 1 素材 B | 一覧 +KB | 読む回数 | またぐ MB |
| --- | ---: | ---: | ---: | ---: | ---: | ---: |
| `inline` | 68.56 | **6202.1** | 6351 | 0.0 | 0 | 0.00 |
| `section` | 67.15 | **315.1** | 323 | 4447.0 | **1** | 4.34 |
| `scattered` | 67.15 | 316.2 | 324 | 4447.0 | **1000** | **66.78** |

同じファイルを実際に読み直したとき（交互 9 巡の中央値・括弧は最小〜最大）:

| 置き所 | 開くだけ ms | 一覧まで ms | 絵 1 枚 ms |
| --- | ---: | ---: | ---: |
| `inline` | 26.9（24.7〜28.1） | 27.9（27.2〜31.0） | 28.6（26.6〜33.0） |
| `section` | **2.7**（2.4〜3.1） | **6.8**（6.2〜11.8） | **2.9**（2.8〜3.1） |
| `scattered` | 2.4（2.2〜4.9） | **52.9**（48.2〜72.6） | 2.5（2.3〜3.1） |

**既定は `section`。** 見出しが 6.2MB → 315KB（**20 分の 1**）、開くだけなら 26.9 → 2.7ms（**10 倍**）、
一覧まで足しても 27.9 → 6.8ms（**4.1 倍**）、絵 1 枚なら 28.6 → 2.9ms（**10 倍**）。
ファイルも base64 が落ちるぶん 68.56 → 67.15MB。

**積み残しが心配していた「一覧を出すのに実体域を読む」は本物だった。ただし散らした場合だけ。**
`scattered` は一覧が 52.9ms で、**追い出したのに `inline` より 1.9 倍遅い**。
読む量（4447KB）は `section` と 1 バイトも変わらないのに、**読む回数が 1 → 1000**、
その 1000 回が **66.78MB にわたって散る**。速さを決めていたのは読んだ量ではなく**届き方**で、
9/28（1 回目）に実体の側で出たのと同じ形（`README.md` の 4）。
**域を 1 つ挟むだけで、その心配だけが外れる。**

### 6.3 追い出した先では生バイトで置く

`section` / `scattered` では base64 を剥がして**生の JPEG** を置く。1.333 倍がそのまま落ちるのと、
読む側が `URL.createObjectURL(blob.slice(…))` で**文字列を 1 本も作らずに**絵にできるため。
**見出しに置いたままではどちらも取れない。**

**剥がせないものは追い出さない**（`thumbs.ts` の `splitDataUrl` が `null` を返す側）。
`thumbnail` が空の音の素材、外部 URL、base64 が壊れているもの、base64 でない素の data URL。
ここを黙って落とすと、**開いた側でサムネイルだけ消える**。

### 6.4 壊れ方の重さが、実体とサムネイルで違う

サムネイル域の長さ（`thumbBytes`）は**実体域の先頭そのもの**なので、
そこが短い側にずれると実体の位置も長さも辻褄が合ったまま**中身だけ別物**になる。
長さは通るので気づけない。なので:

| | どうする |
| --- | --- |
| `section` で域の長さが読めない・負・小数 | **断る**（0 へ丸めて進めない） |
| `section` で域がファイルの外へはみ出す | **断る**（途中で切れている） |
| `section` で絵が域からはみ出す（＝域の長さが疑わしい） | **断る**（実体が全部ずれるので） |
| `scattered` で絵が範囲外 | **その 1 枚だけ**落として名前を出す |
| 実体が範囲外 | その 1 つだけ落として名前を出す（元から） |

落ちた絵の名前は `thumbsOutOfRange` に、落ちた実体は `outOfRange` に、**別の列で**出す。
絵が出ないのと素材が開けないのは人にとって重さがまるで違うので、混ぜると本題が埋もれる。

## 並べ方（`src/container.ts`）

```
[0,8)              "VIVIDPK1"         目印
[8,12)             uint32LE           見出しの**バイト**長 H
[12,12+H)          見出し（UTF-8 の JSON）
[12+H, +D)         ハッシュ域（長さ D ＝ 見出しの digestBytes。`digests: 'section'` のときだけ）
[12+H+D, +T)       サムネイル域（長さ T ＝ 見出しの thumbBytes。`thumbs: 'section'` のときだけ）
[12+H+D+T, …)      実体。見出しの bodies の順に、隙間なく並べる
```

決めるのに引っかかった所が 3 つある。

**位置は「その域の先頭から」の相対で持つ。** ファイル先頭からの絶対位置で書くと、
位置の桁が伸びたぶん見出しが伸びて、その伸びたぶん位置がずれる（不動点を解く話になる）。
域の先頭を 0 にすれば、見出しの長さと位置が切り離せて 1 回で決まる。
**サムネイル域を挟んでも同じで**、T は見出しの長さに依らないので不動点は出てこない
（`section` の絵はサムネイル域の先頭から、`scattered` の絵は実体域の先頭からの相対）。
**ハッシュも同じ。** 域の長さ D は「32 × 実体の数」で、実体を 1 バイトも読まずに決まる。
おかげで**ハッシュを後から足しても実体の位置が 1 つも動かない**（見出しが伸びるだけ）——
`layoutPack` で場所を決めて、`attachDigests` で中身を入れる形が取れるのはこのため。

**見出しの長さは「文字数」ではなく「バイト数」。** 素材名に日本語が入ると
JSON の文字数と UTF-8 のバイト数がずれる（測ったら 387 文字 = 423 バイト）。
文字数で書くと見出しの終わりが手前にずれて、実体の頭が見出しに食われる。

**詰める順は id の昇順。** `usedMediaIds` が返す順はクリップの並びに依るので、
そのまま詰めるとクリップを 1 つ動かしただけで実体の位置が全部ずれる。
それでは「同じプロジェクトを 2 回書き出したら同じファイルになる」が崩れて、差分も取れない。

## 7. 壊れを見つける値（ハッシュ）を入れた（2026-09-28・3 回目）

9/28（1 回目）にはここに「**入れない**」と書いてあった。理由は 2 つ挙げてあった。

> (a) 速さは理由にならない（96MB の sha256 は 79ms で、**書く時間より軽い**）
> (b) `crypto.subtle.digest` には流し込む口が無いので、入れると「実体をメモリに乗せない」が消える

**測り直したら、(b) は「ファイル全体で 1 つ持つ」ときだけの話で、(a) は逆だった。**
素材ごとに分けると (b) は消え、代わりに (a) が費用として残る（`npm run lab:pack:digest`）。

### 7.1 メモリ — 素材ごとに分けると上乗せが 0 になる

12MB × 8 本（96MB）を、別のプロセスで測った山（`mem-probe.mjs`）:

| やり方 | 山 MB | 素材を用意しただけを引いて |
| --- | ---: | ---: |
| 素材を用意しただけ | 0.00 | — |
| 二進に並べる（ハッシュなし） | 0.00 | 0.00 |
| **素材ごとにハッシュ**（1 本ずつ読んで捨てる） | 0.00 | **0.00** |
| ファイル全体で 1 つのハッシュ | 251.71 | **+251.71** |

**まるごとは実体の 2.62 倍を積む。** 繋げた写し（96MB）と `subtle.digest` が中で作る写し（96MB）を
同時に抱えるためで、**JSON に base64 で埋めるのと同じ穴**（README の 3）。
素材ごとに分ければ写しは 1 つも増えない。ブラウザではここが
「いちばん大きい素材 1 本ぶん」になる（`Blob.arrayBuffer()` で起こすので）。

### 7.2 速さ — 「書く時間より軽い」は、別々の測りを並べたものだった

**同じ回の中で交互に回す**と（9/26 に `export-cost` が確定させた形。96MB・8 本）:

| やること | ms | 最小〜最大 |
| --- | ---: | --- |
| 書く | 153.5 | 118.7〜260.2 |
| ハッシュ（素材ごと 8 本） | 346.2 | 299.0〜407.7 |
| ハッシュ→書く | 470.9 | 438.9〜986.4 |

**ハッシュは書く時間の 2.25 倍。書く段ぜんたいは 3.07 倍**（154 → 471ms ≒ 3.6ms/MB）。
元の「79ms 対 55ms」は、**別々の測りから並べた数字**だった。
しかも**書く段は 2.2 倍振れる**（119〜260ms）ので、倍率そのものが 1.15〜3.44 倍まで動く。
**「A より軽い」と言う前に、A が何倍振れるかを見ること。**

ハッシュのやり方も並べた（同じ 96MB）:

| やり方 | ms | MB/s |
| --- | ---: | ---: |
| `crypto.subtle`：素材ごと 8 回 | 332.7 | 289 |
| `crypto.subtle`：まるごと 1 回 | 364.4 | 263 |
| `node:crypto`：素材ごと 8 回 | 275.3 | 349 |
| `node:crypto`：流し込み 1 つ | 292.4 | 328 |

**素材ごとに分けても遅くならない。むしろ速い**（まるごとは 1.10 倍遅い。写しを作る手間のぶん）。
「流し込めるほうが得」という見込みも外れていて、`node:crypto` でも差は 1.06 倍しか無い。
ブラウザの `subtle` は `node:crypto` の 1.21 倍遅いが、**判断する所はブラウザと同じ道で書く**
（`digest.ts` の注）。

### 7.3 置き所 — サムネイルと答えが逆になった

素材 1000 個・実体 64KB ずつ（`npm run lab:pack:digest`）:

| 置き所 | 見出し KB | 1 素材 B | 域 KB | 全体 MB | 開く ms | 全部確かめる ms | 抜き取り 1 本 |
| --- | ---: | ---: | ---: | ---: | ---: | ---: | ---: |
| `none` | 315.2 | 323 | 0.0 | 67.15 | 5.20 | — | — |
| **`header`（既定）** | 367.9 | 377 | 0.0 | 67.20 | 5.77 | 659 | 24.9ms / 64KB |
| `section` | 315.2 | 323 | 31.3 | 67.18 | 6.48 | 583 | 22.8ms / 95KB |

**追い出しても開く時間が動かない。** 3 つとも振れ幅（4.1〜17.3ms）の中に収まる。
6.2 で絵を追い出したときは 26.9 → 2.7ms と **10 倍**動いたので、同じ形の話ではない——
**効くかどうかは置くものの大きさで決まる**（絵 1 枚 5KB 対 ハッシュ 1 つ 44 バイトで 100 分の 1）。
見出しの太りは 1 素材 54 バイトなので、**絵が 1000 個で当たった壁（6.2MB）にハッシュが当たるのは
素材 10 万個から。**

差が出ないなら**形が単純なほうを採る**。既定は `header`（見出しの `bodies` の中）。
`section` を選ばなかったのは、域を 1 つ増やすと (1) その長さが実体の位置を全部動かすので
断る条件がまた 1 つ増え、(2) 域の中の順番を**落とした実体を数える前の並び**で合わせる必要が出る
（`digestAt`。ここは実際に 1 つずれる形を検算で踏んだ）から。

**番号はファイルに書かない**、というのが 7.3 のもう 1 つの収穫。最初は `section` のときに
「域の何番目か」を見出しに書いていたが、それだと**見出しから追い出すために足した形が
見出しを 14.5KB 太らせる**（素材 1000 個）。域は見出しの `bodies` と同じ順なので、
読む側が数えれば要らない。

### 7.4 何を見つけて、何を見つけないか

素材 6 本のファイルをわざと壊して確かめた:

| 壊し方 | 位置だけで（9/28 までの形） | ハッシュで | 抜き取り 1 本 |
| --- | --- | --- | --- |
| 実体の中の 1 バイトが化けた | **気づけない** | 1 / 6 本が違う | 見つからない |
| 同じ長さの実体が入れ替わった | **気づけない** | 2 / 6 本が違う | 見つかる |
| サムネイル域が 1 **短い** | 断る（開く前。6.4 の門） | — | — |
| サムネイル域が 1 **長い** | 実体 1 本が範囲外 | **5 / 5 本が違う** | 見つかる |
| 末尾が切れている | 実体 1 本が範囲外 | 0 / 5 本が違う | 見つからない |

**ハッシュが足すのは「読めるが中身が違う」の列だけ。** 切れている・はみ出しているのは、
もともと位置で見つかっていた（`outOfRange`）。

いちばん効くのは**サムネイル域が長い側へずれた形**。6.4 の門は「絵が域からはみ出す」を見るので、
**域が長くなる側は素通りする**——そのとき実体の位置は全部ずれるのに、位置と長さの辻褄は合う。
6.4 に「長さは通るので気づけない」と書いた形がこれで、**見つけたのは 1 本だけ範囲外**という
ぼやけた形だった（残り 5 本は黙って別物が開く）。ハッシュを入れると 5 本とも「違う」と言える。

**域のずれは、いちばん小さい実体 1 本を抜き取るだけで見つかる**（64KB・24.9ms 対 62.5MB・659ms）。
ずれは全部の実体を同じだけ動かすので、どれか 1 本を引けば必ず出る。
逆に**「1 本だけ中身が化けた」は抜き取りでは出ない**（その 1 本を引かないと分からない）。
→ **「入れ替わりは抜き取りで見つかる」の行だけは、1 本目を壊した場合の話だった**
（2026-09-29 に 5・6 本目で試したら出ない。8.2 の表）。
`verifyPack` の `sample` はこの 2 つを分けて使うためにある。
**0 バイトの実体は抜き取りに選ばない**——読む量 0 で済むが、位置がずれていても
0 バイトのハッシュはいつでも合うので、見つける役に立たない。

### 7.5 決めたこと

- 素材ごとに 1 つ。**ファイル全体で 1 つにはしない**（7.1）。
- **開くときには計算しない。「確かめる」ときだけ**（`openPack` は見出しだけで済ませる）。
- 合わなかった実体は**落とすが、ファイルは断らない**。列は `outOfRange` と分ける
  （「読めない」と「読めるが中身が違う」は人に伝えることが違う）。
- ハッシュが書かれていないものは**`unknown`（分からない）**。壊れていることにしない。
  そこは**読みもしない**（読んでも分かることが増えない）。
- 埋め忘れたまま書けないようにする。`attachDigests` を通さずに `realizePack` を呼ぶと断る
  （空の域を書くと、壊れていないのに**全部が「中身が違う」**になる）。

## 8. ハッシュを「端だけ」で取る形（2026-09-29）

9/28（3 回目）の積み残しの筆頭。7.2 のとおり費用は全部**「実体を丸ごと読む」**に出るので、
端の数十 KB だけを混ぜれば **100 分の 1 になるはず**——という見込みだけが書いてあった。
測った（`npm run lab:pack:edge`）。**見込みは半分当たり、結論は「端だけでは置き換えられない」。**

### 8.1 端だけの覆いは「読んだ量 ÷ 実体の大きさ」そのもの

1 バイトの化けを実体の全域に等間隔で 201 か所置いて、端だけが見つけた割合:

| 実体 | 端 4KB | 端 64KB | 端 256KB |
| --- | ---: | ---: | ---: |
| 96KB | 9.0% | **100%**（端＝全部） | **100%** |
| 512KB | 2.0% | 25.4% | 100% |
| 4MB | 1.0% | 4.0% | 12.9% |
| **12MB**（切り抜きの素材 1 本） | 1.0% | **2.0%** | 5.0% |

**確率の話ではなく、覆いの話。** 端だけの形は「実体の何割を見るか」を選んでいるだけで、
12MB を 64KB×2 で見るなら**中身の化けは 98% 見逃す**。
つまみ（N）で買えるのは覆いそのもので、そこに得はない。

### 8.2 絞る向きが 2 つある。**4 象限で見ると、見落とすものが違う**

7.4 の「抜き取り 1 本」は*素材*を絞る手、端だけは*1 本の中*を絞る手で、**直交している**。
実体 1MB × 6 本・端 64KB でわざと壊した:

| 壊し方 | 位置だけ | 全部×丸ごと | 全部×端 | 1 本×丸ごと | 1 本×端 |
| --- | --- | --- | --- | --- | --- |
| 実体の先頭 1 バイト | 気づけない | ○ | ○ | × | × |
| **実体の中ほど 1 バイト** | 気づけない | ○ | **×** | × | × |
| 実体の末尾 1 バイト | 気づけない | ○ | ○ | × | × |
| **中ほどの 4KB が零で埋まった** | 気づけない | ○ | **×** | × | × |
| **端は同じで、中だけ別物** | 気づけない | ○ | **×** | × | × |
| 実体が入れ替わった（1・2 本目） | 気づけない | ○ 2 本 | ○ 2 本 | ○ | ○ |
| 実体が入れ替わった（5・6 本目） | 気づけない | ○ 2 本 | ○ 2 本 | **×** | **×** |
| サムネイル域が 1 長い（門を素通り） | 範囲外 1 本 | ○ 5 本 | ○ 5 本 | ○ | ○ |
| 末尾が切れている | 範囲外 1 本 | × | × | × | × |
| **見出しの `edgeBytes` が化けた** | 気づけない | × | **○ 6 本（誤警報）** | × | ○（誤警報） |

読む量: 全部×丸ごと 6144KB / 全部×端 768KB / 1 本×丸ごと 1024KB / **1 本×端 128KB**。

- **端だけが取り落とすのは「中身の化け」だけで、そこは丸ごとにしか見えない。**
  下の 3 つ（中ほど 1 バイト／4KB の零／端は同じで中だけ別物）は**わざと端を避けて作った素材**で、
  3 つとも端では 1 本も出ない。実体の入れ替わりとずれは端でも全部出る（頭も尻も同じだけ動くので）。
- **抜き取りが取り落とすのは「どの素材か」。** 同じ入れ替わりでも、
  1・2 本目なら抜き取りで出て、5・6 本目なら出ない（`cheapestFirst` が引くのは 1 本目）。
  **7.4 で「入れ替わりは抜き取りで見つかる」と書いたのは、たまたま 1 本目を壊していたから。**
  ずれだけは必ず出る（全部の実体を同じだけ動かすので、どの 1 本を引いても外れない）。
- **端だけには、丸ごとに無い弱みがある。** 見る幅を見出しに預けているので、
  **`edgeBytes` が読める形のまま書き換わると、壊れていない実体まで「中身が違う」と言い出す**
  （6 本とも）。丸ごとは読む範囲が実体の位置だけで決まるので動じない。
  読めない形（負・小数・文字）に化けたときは 0 へ倒して「分からない」にする——**断らない**。
  端が化けただけで、中身の読めるファイルを開けなくするのは割に合わない。

### 8.3 費用 — 書くのは 25 分の 1 になる。**ただし「添える」なら測れないほど安い**

96MB（12MB × 8 本）・同じ回の中で交互に（`LAB_PACK_ROUNDS=7`）:

| やること | ms | 実体を読む量 |
| --- | ---: | ---: |
| 書く：丸ごとだけ | 92.6（83.9〜106.3） | 96.00MB |
| **書く：端だけ** | **3.7**（3.0〜4.1） | **1.00MB** |
| 書く：両方（既定） | 90.7（86.5〜103.1） | 96.00MB |

| 確かめる | ms | 読む MB |
| --- | ---: | ---: |
| 全部×丸ごと | 84.53 | 96.000 |
| 全部×端 | 3.22 | 1.000 |
| 1 本×丸ごと | 13.70 | 12.000 |
| **1 本×端** | **0.78** | **0.125** |

- **読む量が 96 分の 1 でも、時間は 25 分の 1 しか下がらない**（0.96ms/MB 対 3.71ms/MB）。
  1 本あたりの手間（2 回の切り出しと繋ぎと `subtle.digest` の呼び出し）が残るため。
  「100 分の 1 になるはず」は**読む量の話としては当たり、時間の話としては 4 倍外れる。**
- **添えるぶんの上乗せは測れない。** 両方持っても読む量は 1 バイトも増えない
  （同じ 1 回の読みから両方を作る）ので、差は書く段の振れ（1.27 倍）の中に入る。
- **端のいちばんの値打ちは「素材の大きさに依らない」こと。** 抜き取り 1 本の費用は
  *いちばん小さい実体*の大きさで決まるので、素材が全部大きいと抜き取りでも秒になる
  （12MB で 13.70ms、1 時間の素材なら 4 秒級）。端なら 128KB・0.78ms で固定。

### 8.4 決めたこと

- **既定は「丸ごとに添えて、端も持つ」**（`layoutPack` の `edges` の既定 = 64KB）。
  端だけを唯一の持ち方にはしない（8.1 の 98% と 8.2 の誤警報）。
  `digests: 'none'` のときだけ 0——あれは「9/28 までの形」を比べるための置き所で、
  そこに端を足すと**端が唯一のハッシュになった形**が既定で出てくる。
- **確かめる段で選ぶ**（`verifyPack` の `depth`）。`full` が既定。
  `edge` は**ずれと入れ替わり専用の安い検査**で、`full` の安い版ではない。
- **ハッシュは書くときにしか作れない**ので、使う口（開いたときに黙って 1 本確かめる等）を
  決める前でも書いておく。上乗せが測れない大きさなのが、そう決められる理由。
- **2N 以下の実体には端のぶんを書かない。** そこは端＝全部で、書くと同じ 44 文字が
  見出しに 2 つ並ぶだけ。読む側は長さから境界を出して、丸ごとのぶんで端を確かめる。
- **幅が無いときに既定の幅で埋めない。** 埋めると、その幅より小さい実体では
  「端＝全部」が成り立って**端の検査が黙って丸ごとの検査に化ける**（検算が捕まえた穴）。

### 8.5 測って気づいたこと（次の回の自分へ）

- **既定を変えた日は、その既定を「比べる相手」にしていた測りが全部おかしくなる。**
  9/28 の測り（`lab:pack:digest` / `mem-probe`）には `edges: 0` を足したのに、
  **同じ日に新しく書いた `edge-probe` の中で同じ穴を踏んだ**——「丸ごとだけ」の行が
  既定で端を持ち、**同じものを 2 回測って「差は 1.09 倍」**と読んでいた。
  比べる相手は**既定を使わずに書く**こと。
- **「端は同じで中だけ別物」のような素材を先に作っておくと、結論がひっくり返らない。**
  7.4 の 5 つだけなら「端で 4 つ取れる」と読めてしまう。
  端を避けて作った 3 つを足すと、取れているのは**壊し方の種類ではなく壊れる場所**だと分かる。
- **「抜き取りで見つかる」は、壊した場所に依っていた**（上の 5・6 本目）。
  7.4 の表のうち「入れ替わりは抜き取りで見つかる」だけは、**1 本目を壊した場合の話**。

## 9. 端の幅を素材の大きさで変えるか（2026-09-29・2 回目）

`npm run lab:pack:width`。8 の積み残しの筆頭。
8.1 で**端だけの覆いは「読んだ量 ÷ 実体の大きさ」そのもの**だと分かったので、
幅が固定（64KB）だと**大きい素材ほど覆いが薄くなる**。
積み残しには「『長さの 1%』なら覆いは揃うが費用が大きさに比例して戻る」と書いてあった。
**その交換が本当に交換なのかを測った。答えは「交換ですらない」。**

**結論を 2 行で。幅は変えない（大きさで変えても買えるものが無い）。
代わりに、同じ読む量を 3 個に分けて散らす（既定を `edgePieces: 3` にした）。**

### 9.1 幅で買えるのは確率だけ。しかもその確率は読む量そのもの

実体 12MB に 1 バイトの化けを **2000 か所**（種を固定した乱数で置く）:

| 幅の方針 | 幅 N | 読む量 | 覆い | 見つけた |
| --- | ---: | ---: | ---: | ---: |
| 固定 4KB | 4KB | 8KB | 0.1% | 0.1% |
| 固定 64KB | 64KB | 128KB | 1.0% | 0.9% |
| 固定 256KB | 256KB | 512KB | 4.2% | 4.0% |
| 長さの 0.5% | 61KB | 123KB | 1.0% | 0.9% |
| 長さの 5% | 614KB | 1.20MB | 10.0% | 10.0% |

**覆いと「見つけた割合」は同じ数。** だから「長さの 0.5%」にして覆いを大きさによらず
1.0% に揃えても、**揃えた先が 1.0% のまま**で、費用だけが大きさに比例して戻る
（96MB の素材で 1 本 983KB）。**幅は丸ごとへの近道ではない。**
100% が欲しいなら丸ごと読むしかなく、8.4 で「丸ごとに添える」を既定にしたのはそのため。

### 9.2 効くのは幅ではなく、同じ量を**どこで**読むか

合計 2N（＝128KB）を変えずに、実体の端から端まで `pieces` 個に分けて置く。
**`pieces = 2` は先頭 N ＋末尾 N そのもの**なので、「端だけ」は散らし方の 1 つでしかない。

| 散らし方 | 読む量 | 覆い | 全域の 1B | 全域の 4KB | **頭 64KB の中** | **尻 64KB の中** |
| --- | ---: | ---: | ---: | ---: | ---: | ---: |
| 2 個（＝端だけ） | 128KB | 1.0% | 0.9% | 1.0% | **100%** | **100%** |
| **3 個（既定）** | 128KB | 1.0% | 1.4% | 1.1% | 66.1% | 67.9% |
| 4 個 | 128KB | 1.0% | 0.9% | 0.9% | 50.9% | 51.2% |
| 16 個 | 128KB | 1.0% | 0.9% | 1.6% | 12.6% | 13.1% |
| 64 個 | 128KB | 1.0% | 0.7% | 2.9% | 3.3% | 3.2% |

**全域に散らした化けは、散らし方で変わらない**（覆いが同じなので当然）。
4KB のブロックだけ散らすほど高いのは、読む所との「重なりしろ」が 4KB ぶん広いから。

右の 2 列が**散らす案を潰しにいった所**。容器の見出しは実体の頭にあるので、
「開けない壊れ方」はそこに集中しやすい。**端だけはそこを丸ごと見るが、散らすと薄くなる。**

### 9.3 それでも散らす理由——端だけには、幅で埋められない穴がある

`pseudoBytes` は全域が乱数なので、**どの 1 バイトを見ても実体どうしが違う。**
本物はそうではない。同じ設定で書き出した動画は**頭に同じ容器の見出し**が付き、
形式によっては**尻も同じ形で終わる**（零詰め）。そういう素材を作って
（`boilerplateBytes`）、同じ長さの 2 本を入れ替えてみる:

| 素材 | 端 4KB | 端 64KB | 端 256KB | 端 1MB | 散らす 3 | 散らす 16 | 丸ごと |
| --- | :-: | :-: | :-: | :-: | :-: | :-: | :-: |
| 全域が乱数（いままでの素材） | ○ | ○ | ○ | ○ | ○ | ○ | ○ |
| 頭 256KB が同じ | ○ | ○ | ○ | ○ | ○ | ○ | ○ |
| 尻 256KB が零 | ○ | ○ | ○ | ○ | ○ | ○ | ○ |
| **頭 256KB＋尻 256KB** | × | × | × | ○ | ○ | ○ | ○ |
| **頭 2MB＋尻 2MB** | × | × | × | × | ○ | ○ | ○ |

**端が破れるのは「幅が決まり文句より広いとき」だけ。そして決まり文句がどこまで続くかは、
書く側に分からない。** 幅では守れない——2MB 揃っていれば端 1MB でも見落とす。
**片方が揃っているだけでは破れない**（頭だけ・尻だけの行が全部 ○）のも測って分かったこと。
散らすと、**幅を 1 バイトも広げずに**そこへ届く。**3 個でもう届く**——真ん中に 1 つ置くだけ。

### 9.4 費用は「量」ではなく「回数」で払う

| | 2 個 | 3 個 | 4 個 | 16 個 | 64 個 | 256 個 | 丸ごと |
| --- | ---: | ---: | ---: | ---: | ---: | ---: | ---: |
| メモリの上 | 0.215 | 0.197 | 0.227 | 0.222 | 0.228 | 0.309 | — |
| **ファイルの上** | **0.332** | **0.407** | 0.472 | 0.998 | 2.918 | 11.537 | 14.584 |

（ms・12MB の実体 1 本・交互 9 巡の中央値。読む量はどれも 128KB）

**メモリの上では回数がほとんど効かない**（`subarray` は写しを作らないので読む手間が無い）。
**回数の代価はファイルの上に出る**——1 回あたり 0.042ms。これがブラウザの
`Blob.slice(…).arrayBuffer()` にあたる。2 個 → 3 個で 0.33 → 0.41ms、丸ごとの **2.8%**。
幅のほうは素直に量に比例する（端 64KB 0.41ms / 端 1MB 2.49ms / 丸ごと 11.87ms）。

**「覆いを買う」と「散らし方を買う」は値段が違う。覆いは量で、散らし方は回数で払う。**
そして 9.1 のとおり、量で買える覆いは端の検査を丸ごとの代わりにはしてくれない。

### 9.5 決めたこと

- **幅 N は素材の大きさで変えない。64KB 固定のまま。**
  理由は 8.3 の「費用が定数だから」ではなく、**9.1 の「覆いを買っても届かないから」**に変わった。
  長さに比例させる方針（`0.5%` / `挟む`）は**測って捨てた。**
- **既定の散らし方は 3**（`DEFAULT_EDGE_PIECES`）。読む量は 1 バイトも変わらない。
  2 個が**原理的に取れない**相手（9.3）を、幅を広げずに取れるようにするため。
- **代価は書いておく。** 頭・尻に集中した化けが 100% → 66%、ファイルの上で 0.33 → 0.41ms。
  **どちらも一方が他方を覆わない**ので、`edgePieces` は書く側も読む側も選べる。
  検算には**両向き**を固定してある（3 が勝つ場合と 2 が勝つ場合の両方）。
- **`edgePieces` が見出しに無いファイルは 2 として読む**（`LEGACY_EDGE_PIECES`）。
  9/29（1 回目）に書いたファイルがそれ。**無い欄に入れるのは「いまの値」ではなく
  「そのとき何だったか」**——いまの既定（3）で埋めると、昔のファイルの端が全部
  「中身が違う」になる（しかも丸ごとは合うので、人には意味が分からない）。
- **欄があるのに読めないときは、幅ごと 0 へ倒す**（端は「分からない」）。
  見る所が決まらないので確かめようがない。断りはしない（幅が読めないときと同じ）。
- **散らし方には上限を置く**（`MAX_EDGE_PIECES` = 1024）。**この数はそのまま
  読む口を叩く回数**なので、壊れた見出しが `1e9` と言っただけで**1 バイトも読む前に**
  読み所を並べに行って落ちる（差分を粗探しして見つけた穴。外すと検算がその場で落ちる）。
  1024 に置いたのは、**256 個で既に丸ごとと同じ桁**だから（9.4）。
  上限超えは**丸めずに「読めない」側へ倒す**——丸めると、5000 と書いてあるファイルを
  1024 で読んで「中身が違う」と言い出す（嘘をつく口を増やさない）。
  **書く側も同じ上限で止める**ので、自分で読めない数は書かない。

### 9.6 測って気づいたこと（次の回の自分へ）

- **「等間隔に置いた壊れ」を「等間隔に置いた読み所」で測ると、周期が噛み合って嘘をつく。**
  1 回目の測りで、散らし 16 個の 4KB ブロック検出が **11.8%**（覆い 1.0% の 11 倍）と出た。
  噛み合わせが作った数で、散らし方の手柄ではない。**種を固定した乱数で置けば消える。**
  ついでに、等間隔だと**両端（0 と末尾）が必ず当たる**ので、覆い 0.1% の方針まで
  「1.0% 見つけた」と言い出す（201 か所のうち 2 か所ぶん）。
- **「交互に回す」も「順番を巡回でずらす」も足りない。** 9/26 が確定させた交互は
  巡の中の順番が固定で、**各巡の 1 番目だけが掃除を払う。** 巡回でずらしても
  `cases[(i + r) % n]` は**隣り合わせをそのまま残す**ので、重い案（丸ごと 12MB）の次は
  いつも同じ案になり、その案だけが毎巡それを払う。
  実際「128KB を 2 個」が 2.63ms と、同じ量を読む他の案の 4 倍に見えた。
  **種を固定して毎巡シャッフルし、捨て巡を 1 つ置く**まで直らない。
- **既定を変えた日は、その既定を「比べる相手」にしていた測りが全部おかしくなる**（8.5 の再掲）。
  今回も踏みかけた——`edge-probe`（8 の表）は `edgeRanges` を省いて呼んでいたので、
  既定を 3 にした瞬間に**「端だけは中ほどを見逃す」の表が中ほどを見つけ始める。**
  `EDGE_PIECES = 2` を明示して塞いだ。**自分が動かした既定は、自分の測りにも降ってくる。**
- **検算の中の「当たらない位置」も直書きしない。** 「頭に集中した化けは 2 個のほうが強い」を
  40000 B 直書きで書いたら、その位置が散らし 16 個の読み所の中に入っていて落ちた。
  **読み所を計算して、そこから外れる位置を探す**形に直した（探す所が無ければそれも落ちる）。

## 壊れたファイルの扱い

**1 つ壊れていても全部を捨てない。** 本体の `parseProjectFile` も形の合わない素材だけを落としている。
ただし黙って落とすと「開いたら一部が黒い」になるので、名前を `outOfRange` に出す
（本体の `localOnly` と同じ扱い。「この 3 つは運べません」の方が扱いやすい）。

断るのは、ファイルとして読み進められないときだけ:

| | どうする |
| --- | --- |
| 短すぎる / 目印が違う | 断る |
| 見出しがファイルの外へはみ出す（途中で切れた） | 断る |
| 見出しが JSON でない | 断る |
| 新しい版 | 断る（「アプリを新しくしてから」と言う） |
| トラックが無い | 断る |
| **サムネイル域の長さが読めない・負・小数**（`section`） | **断る**（0 へ丸めて進めない。6.4 を参照） |
| **サムネイル域がファイルの外へはみ出す / 絵が域からはみ出す** | **断る**（実体が全部ずれるので） |
| **ハッシュ域の長さが読めない・負・小数・32 の倍数でない**（`section`） | **断る**（同じ理由。7.3 を参照） |
| **ハッシュ域がファイルの外へはみ出す** | **断る**（途中で切れている） |
| **端の幅（`edgeBytes`）が読めない・負・小数** | **断らない。0 へ倒す**（端は「分からない」・丸ごとはそのまま効く。8.2） |
| **散らし方（`edgePieces`）が無い** | **2 として読む**（9/29・1 回目までの「端だけ」。いまの既定で埋めない。9.5） |
| **散らし方が読めない・2 未満・小数・1024 超え** | **断らない。幅ごと 0 へ倒す**（見る所が決まらないので「分からない」。9.5） |
| 実体の位置が範囲外・負・小数 | **その素材だけ**落として名前を出す（`outOfRange`） |
| サムネイルの位置が範囲外（`scattered`） | **その 1 枚だけ**落として名前を出す（`thumbsOutOfRange`） |
| **実体の中身がハッシュと合わない** | **その素材だけ**落として名前を出す（`verifyPack` の `mismatch`） |

**中身が合っているかは、開くときには見ない。**「確かめる」ときだけ（`verifyPack`）。
開くのに要るのは見出しだけなので、そこへハッシュを持ち込むと 10GB のファイルでも
一瞬で開く利点が消える。見つかるもの・見つからないものは 7.4 の表にある。

**まだ見ていないもの**: `scattered` では絵と実体が同じ域に居るので、
**絵の位置が実体と重なっていても通る**（既定は `section` なので実害は無い。
比べる相手として残してあるだけ）。

## 本体へ持っていくときに要るもの

`src/plan.ts` と `src/container.ts` と `src/thumbs.ts` と `src/digest.ts` だけ。
どれも DOM にも Node にも依存していない
（`TextEncoder` / `DataView` / `crypto.subtle` しか使っていない）。`json-pack.ts` は比べるために書いたもので、
測り終わったので持っていかない。

本体側で足すことになるのは:

- `MediaAsset` に `mime` を持つ（埋めた実体を `new Blob([bytes], { type })` で戻すのに要る）。
  いまは `File.type` を捨てているので、`media.ts` の `add()` で拾う必要がある。
- `mediaRegistry.adopt()` に「実体つきで迎え入れる」口。
  いまの `adopt` は参照素材（`src` あり）しか受けない。
- `BodySource` に `slice`（`Blob.slice(from, to).arrayBuffer()`）。**無くても動く**が、
  「端だけを書く」形はこれがあるときだけ安くなる（無いと丸ごと読んでから端を切るので
  費用は 1 バイトも下がらない。8.3）。既定の「添える」形では要らない。
- 書き出しは `await attachDigests(layout, bodies)` を通してから
  `saveBlob(new Blob([layout.prefix, ...layout.parts の Blob]))`。
  **`attachDigests` はここで初めて実体を読む**（1 本ずつ、96MB で 0.35 秒ぶん。7.2）。
  忘れると `realizePack` が断る。
  `JSON.stringify` を通さないので、素材が何 GB あっても文字列の壁に当たらない。
  **`order` ではなく `parts` を並べる**（`section` ではサムネイル域が先に来るので、
  実体だけを並べると前置きと実体の間が空く）。
- 開いた側でサムネイルを戻す所。`MediaAsset.thumbnail` は data URL の文字列なので、
  **そのままでは `section` の値打ちが消える**（読んだ生バイトを base64 へ戻すことになる）。
  `URL.createObjectURL(blob.slice(start, end))` を入れられるかは本体側の話で、
  **ここは測っていない**（`media.ts` は `url` を Blob URL で持っているので、形は合うはず）。
- 拡張子。いまは `.vivid.json`。中身が JSON でなくなるので `.vividpack` のような別の名前が要る
  （`.json` のまま二進を入れるのがいちばん良くない）。
