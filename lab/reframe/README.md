# reframe — 被写体を追う自動リフレーム

横型（16:9）で撮った素材から縦型（9:16）を切り出すとき、**クロップ枠を被写体に合わせて横へ動かす**。
決めるのは「各コマで、幅 31.6% の窓を横のどこに置くか」の 1 本の列だけ。
縦は切らない（16:9 から 9:16 を切るときに余るのは横だけ）ので、ここも横だけを持つ。

```
npm run lab:reframe          # 実際どれくらい効くか（数字は記録に残す）
npm run lab:reframe:probe    # どの手なら被写体を指せるか（実装する前に）
npm run lab:reframe:v        # **縦の軸**（最初から縦の素材から 1:1 を切る）
npm run lab:reframe:vprobe   # 縦の軸で、どの手なら被写体を指せるか
npm run lab:reframe:decimate # 読むコマの速さで何が変わるか（本物の動画・圧縮の粒込み）
npm run lab:reframe:gate     # 門の形で、焼き直しの再現性がどう変わるか
npm run lab:reframe:demo     # 画面（本物の動画を読んで、切り出した縦型を見る）
npm run lab:reframe:uitest   # 読み込む → 枠を決める → 切り出して見せる、が繋がっているか
npm run lab:test             # 計算が合っているか（合成データ・ブラウザ不要・数秒）
```

## いまの数字（2026-09-25・3 回目 ・15fps・横型から 9:16 ・ 素材 8 本）

| | 値 | 前の門（〜9/25 2 回目） | 比べる相手（ずっと真ん中） |
| --- | --- | --- | --- |
| 被写体を枠に入れた率 | **86.1%** | 87.5% | 37.1% |
| 枠の中心と被写体のずれ（中央値） | **0.033** | 0.057 | 0.250 |
| 被写体の居ない素材で泳いだ量（中央値） | **0.012 / 秒** | 0.006 | 0.000 |
| 同 ・ 動いた量の合計（中央値） | **0.050 / 秒** | 0.042 | 0.000 |
| 同じ動画を焼き直したときの枠の開き（最悪） | **0.0016** | 0.0145 | 0.000 |

**3 回目に門を入れ替えた**（貯めて動き出す形 → 貯めない形）。
入れた率を 1.4 ポイント・泳ぎを少し払って、**ずれ・再現性・短い寄り道への追従**を買っている。
下の「門の形」を参照。

「入れた率」は**被写体の中心が窓に入っているコマの割合**。窓の幅は 31.6% なので、
ずれが 15.8% 未満なら入っている。被写体（横幅 40%）は窓より広いので、
**どこに置いても全身は入らない**——だから中心で数えている。

素材ごと:

| 素材 | 入れた率 | 前の門 | ずっと真ん中 |
| --- | --- | --- | --- |
| `motion`（横切る） | 93.4% | 99.2% | 31.1% |
| `subject-pan`（横切る＋カメラもパン） | 93.4% | 99.2% | 31.1% |
| `subject-pause`（途中で 3.5 秒止まる） | 96.5% | 98.6% | 57.0% |
| `subject-cuts`（後ろで 2 回カット） | 91.8% | 91.0% | 31.1% |
| `subject-static`（右寄りに居続ける） | **100.0%** | 100.0% | 0.0% |
| `subject-decoy`（逆向きに動くおとり付き） | 93.4% | 97.5% | 31.1% |
| `subject-dart`（2 秒で行って戻る） | **97.4%** | 93.3% | 15.4% |
| `crossing-vertical`（縦に横切る） | **22.6%** | 21.5% | 100.0% |

新しい門は死に帯ぶん手前で止まるので、被写体が端（`u` が 0.00 や 0.99）まで行くと詰め切れない。
落ちたコマは 24 本とも端だった。逆に**寄り道する 1 本は上がっている**——
`settle` が消えて、待たずに動き出すようになったため。

最後の 1 本だけ負けている。下の「空いている穴」を参照。
（`subject-dart` は 2026-09-25・2 回目に足した 1 本。9/24 の集計は 7 本での **86.7% / 40.2%** で、
**素材を足したら前の日の集計とは並べられない**ので、上の表は 8 本で取り直した値にしてある。
素材ごとの行は 1 本も動いていない。）

## 測ってから決めたこと

### 被写体を指す手は `spatial`（そのコマの中で色が浮いている列）＋ `peak`

`npm run lab:reframe:probe` で 6 通り × 2 通りを並べて測った。生の位置をそのまま
枠の中心にしたときの「枠に入る率」:

| 手 | 読み方 | 入る率 | 外れる所 |
| --- | --- | --- | --- |
| `diff`（前のコマとの引き算） | 重心 | 64.7% | パンの下で総崩れ |
| `diff` | 山 | 59.9% | 同上 |
| `diffShift`（列をずらして打ち消してから引く） | 山 | 60.3% | 打ち消しても直らない |
| `bg`（列ごとの時間の中央値＝背景と比べる） | 山 | 81.4% | 動かない被写体で 0.0% |
| **`spatial`（コマの中の列の中央値と比べる）** | **山** | **88.2%** | 画面いっぱいの被写体 |
| `either`（上 2 つの大きいほう） | 山 | 88.4% | 増えたぶんが釣り合わない |
| `both`（上 2 つの掛け算） | 山 | 80.1% | 片方が 0 だと消える |

**いちばん素直に見える「動いた所を探す」が、いちばん悪い。** カメラがパンしていると
画面じゅうが動くので、被写体の所だけが立つ理由が無い（`subject-pan` で **2.5%**）。
前のコマを列ごとずらして打ち消しても **4.9%** にしかならない——
打ち消せるのは**カメラの動き**だけで、パンで入ってくる新しい景色は打ち消せないから。

`bg` は 81.4% で 2 番手だが、**`subject-static` で 0.0%**。列ごとの時間の中央値を背景とみなす手なので、
**被写体が一度も動かないと、被写体自身が背景の中央値になる。**
短尺の動画でいちばん多いのは三脚に据えてしゃべる形なので、ここが 0% では使えない。
`either`（2 つの大きいほう）は総合では 0.2 ポイント上だが、**`subject-static` を 100% → 89.2%** に落とす。
増えるぶんが `crossing-vertical`（もともと壊れている 1 本）なので、取っていない。

### 重心ではなく山を取る

`diff/centroid` は `motion` でのずれが 0.011 と `diff/peak`（0.141）より小さい。
これは**引き算が「前の縁」と「後の縁」の 2 つを返す**から
（山はどちらか片方を指し、重心は 2 つの真ん中＝被写体の中心を指す）。
ところが相手が 2 つある素材（`subject-decoy`）では、その重心が**どちらでもない所**を指して
59.8% まで落ちる。`spatial` は縁ではなく面を返すので、山で読んで問題が無い。

### 上下 15% を見ない

短尺の動画は上下に字幕が焼かれていて、**1.5 秒ごとに書き換わる**。
字幕は画面の一部しか占めないのに列の色を動かすので、「そこに何かある」を見る手が拾ってしまう。
上下 15% を落とすと:

| | 帯を外す前 | 外したあと |
| --- | --- | --- |
| `captions-only` の泳ぎ | 0.077 / 秒（4 回） | **0.006 / 秒（1 回）** |
| `captions-only` の振れ幅 | 0.425 | **0.073** |
| 泳ぎの中央値（居ない素材） | 0.043 | **0.006** |
| 入れた率（`crossing-vertical` を除く 6 本） | 97.4% | 96.8% |

**ここは「字幕は上下にある」という入力への仮定**なので、つまみ（`rowBand`）として残してある。

### 「追う」の中身は、ならしではなく「どれだけ動かすか」

生の位置は**当たっているが落ち着きが無い**。そのまま枠にすると 1 コマごとに揺れる。
かといって強くならすと、動き出した被写体に置いていかれる。**遅れと揺れは同じつまみの裏表**なので、
ならす量ではなく**動かし方**を置いた:

1. 生の位置を**中央値**でならす（平均ではない。カットのコマで飛ぶ 1 点を落とすため）
2. ずれが `deadband`（0.03）の内側なら**動かさない**
3. 外へ出たら、**はみ出したぶんだけ**（`maxSpeed` = 0.22 / 秒を上限に）寄せる

2026-09-25（2 回目）までは 3 が「`settle`（0.3 秒）続けて外に居たら動き出し、
`deadband` の 4 分の 1 まで寄せ切って止まる」形だった。下の節を参照。

### 門の形 — 貯めて動き出す形は、59 倍の増幅器だった（2026-09-25・3 回目）

`npm run lab:reframe:gate`。**同じ動画を、焼くビットレートだけ 5 通り変えて焼き直し**、
枠の置き所がどれだけばらけるかを見る（2 回目に作った物差し）。

貯めて動き出す門では、ならした的が**ごくわずか**違うだけで
「動き出す / 動かない」が入れ替わり、枠ぜんたいが死に帯ぶん別の所へ行く。
合成データで測ると **的の差 0.0010 → 枠の差 0.0587（59 倍）**。
`selftest.ts` に 2 件（既定の門は 1 倍 / 貯める門は 59 倍）として固定してある。

**この検算は合成したコマからは書けない。** コマは画素に量子化されているので、
1 画素（0.008）より細かい差が作れず、0.0036 の差を入れようとして
まったく同じコマが 2 枚できた。**検算したい層より粗い入口からは、その層は検算できない**ので、
`planFromRaw()`（生の位置の列を直に取る入口）を分けた。

4 通り測った（30fps 読み ・ 被写体の居る 7 本）:

| 門 | 入れた率 | 焼き直しの振れ幅（最大） | 枠の開き（最悪） | `pan` の泳ぎ | `dart` の寄り道 |
| --- | --- | --- | --- | --- | --- |
| `step`（貯めて動き出す・〜2 回目） | 96.7% | 1.6pt | 0.0145 | 0.033 | 55.0% |
| `release`（捨てる線を下げる） | 96.7% | 1.6pt | 0.0145 | 0.033 | 55.0% |
| `ramp`（比例して貯める） | 96.1% | 2.5pt | 0.0153 | 0.019 | 55.0% |
| **`soft`（貯めない・帯 0.03）** | **95.7%** | **0.4pt** | **0.0016** | **0.029** | **90.0%** |

- **`release` は `step` と 1 桁も違わない**（全素材・全ビットレートで同じ値）。
  捨てる線を 0.6 倍・0.3 倍へ下げても同じなのは、**貯めが捨てられるのが
  「縁をまたいだ 1 コマ」ではなく「寄せ切って止まった所」**だから。
  **「出入りの線を広く取る」は、最初に思いつく手で、何も変えない。**
- **`ramp` は素材によって効いたり効かなかったりする**（`subject-decoy` の枠の開きは
  0.0145 → 0.0005 まで落ちるのに、`subject-pan` は 0.0046 → 0.0115 と上がる）。
  縁ちょうどでは貯めも減りもしない作りなので、**縁に貼り付いた的では永久に動き出さない。**
- **効いたのは、貯めるのをやめること。** 状態を持たない門はどの 1 コマも
  「動き出すか」を決めないので、入力の差がそのまま出力の差になる（1 倍）。

死に帯を 0.06 → 0.03 にしたのは、**`soft` では死に帯が「止まるときに残るずれ」そのもの**になるから。
0.06 のままだと端まで詰め切れず入れた率が 4.6 ポイント落ちる。
0.02 まで詰めると入れた率は戻るが、**`pan` の泳ぎが 0.029 → 0.063 と倍**になる。

#### 泳ぎの数字が増えたぶんの半分は、採点の付け替えだった

`scoreSwim` は「カットの直後に始まった run は組み直しとして外す」形なので、
**枠が止まらずに動き続ける門では、カットの手前から開いた run が丸ごと泳ぎに化ける。**
`cuts-plain` は動いた量の合計が 0.078 → 0.071 と**減っている**のに泳ぎが 0.000 → 0.071 になった。
物差しの側を 2 つ直した（run をカットで切る / 時刻の丸めしろ 1ms）。
**どちらも、前の門の数字を動かさないことを確かめてある**
（20 本のうち `pan-cuts` が 0.085 → 0.076 と動き、その 0.009 は組み直しへ移っただけ）。
`bench.mjs` は**合計の列**も出すようにした——泳ぎと組み直しの境目は run の始まりで決まるので、
合計を並べておかないと「増えた」と「付け替わった」が読み分けられない。

### 頭の置き所は、最初の 0.3 秒から決める（`leadIn`）

真ん中から始めると、右寄りに居続ける被写体では**頭でかならず 1 回すべる**。
編集では頭から最後まで素材が手元にあるので、始まる前に決めてよい。
外すと入れた率は 0.3 ポイント上がる（87.0%）が、**泳ぎが 0.006 → 0.026 と 4 倍**になる。

## 縦の軸（2026-10-04）

最初から縦（9:16）で撮った素材から **1:1** を切ると、余るのは**縦**になる。
決めるのは「各コマで、高さ **56.25%**（＝ 9/16）の窓を縦のどこに置くか」の 1 本の列だけ。

**横の表と入れた率を並べて読まないこと。** 縦の窓（0.5625）は横の窓（0.316）の
**1.8 倍広い**ので、同じ出来でも入れた率は高く出る。並べてよいのはずれと泳ぎのほう。

### いまの数字（15fps ・ 最初から縦 9:16 から 1:1 ・ 素材 6 本）

| | 値 | 横の手をそのまま | 階調だけ外す | 比べる相手（ずっと真ん中） |
| --- | --- | --- | --- | --- |
| 被写体を枠に入れた率 | **96.6%** | 80.5% | 97.4% | 84.7% |
| 枠の中心と被写体のずれ（中央値） | **0.052** | 0.062 | 0.062 | — |
| 居ない素材で泳いだ量（中央値） | **0.002 / 秒** | 0.006 | 0.001 | 0.000 |
| 同 ・ いちばん泳いだ素材（`tilt`） | **0.131** | 0.182 | 0.169 | 0.000 |

素材ごと:

| 素材 | 入れた率 | ずれ | ずっと真ん中のずれ |
| --- | --- | --- | --- |
| `vsubject-static`（上寄りに居続ける） | **100.0%** | 0.051 | 0.100 |
| `vsubject-pause`（縦に動いて 3.5 秒止まる） | 95.4% | 0.052 | 0.172 |
| `vsubject-tilt`（縦に動く後ろでカメラも縦に流れる） | 91.0% | 0.071 | 0.250 |
| `vsubject-cuts`（後ろで 2 回カット） | 93.4% | 0.103 | 0.250 |
| `vsubject-captions`（上下に字幕が書き換わる） | **100.0%** | 0.016 | 0.100 |
| `vsubject-horizon`（空と地面がくっきり分かれる） | **100.0%** | 0.023 | 0.200 |

### 枠を決める段は、そのまま乗った

`planFromRaw` の入口は「0〜1 の位置の列」1 本だけで、**軸を知らない。**
死に帯・寄せる速さ・ならし・門（`soft`）・頭の置き所は 1 つも書き換えずに縦で動いた。
入れ替えたのは**窓の長さ**（0.316 → 0.5625）だけ。

### 被写体を指す手は、作り直しになった

横で勝っている `spatial`（そのコマの中で色が浮いている帯）を**そのまま縦へ当てると 80.5%** で、
**比べる相手（ずっと真ん中 84.7%）に負ける。** 理由は 2 つあって、どちらも
**縦の軸にしか無い事情**だった:

1. **背景の階調は縦に付いている**（空と地面）。帯の色をコマの中の中央値と比べる手では、
   **いちばん浮くのが被写体ではなく階調の端**になる。`vsubject-static` の重みは
   上 0.06 から下 0.26 まで一本調子に上がり、山は必ずいちばん下の帯を指す
   （入れた率 **0.0%** ・ずれ 0.319）。
   → **帯の番号に直線を当てて、その残りだけを見る**（`trendOdds`）。0.0% → **100.0%**。
2. **焼き込みの字幕は上下にある**。横の軸では字幕は軸と垂直なので、畳む前に
   `rowBand` で落とせる。**縦の軸では字幕が軸の上に載っている**ので落とす先が無い。
   → 畳んだあとに締め出す（`axisBand`・上下 15%）。`vsubject-captions` のずれが
   0.119 → **0.016**。

**片方だけでは足りない。** 階調だけ外すと字幕に負け（ずれ 0.119）、締め出しだけだと
階調に負ける（`vsubject-static` 0.0%）。

### 締め出し（`axisBand`）は、入れた率を 0.8 ポイント払って買っている

| | 既定（締め出しあり） | 締め出し無し |
| --- | --- | --- |
| 入れた率 | 96.6% | **97.4%** |
| ずれ（中央値） | **0.052** | 0.062 |
| `vsubject-captions` のずれ | **0.016** | 0.119 |
| `tilt` の泳ぎ | **0.131** | 0.169 |
| `captions-only-sheer` の泳ぎ | **0.090** | 0.148 |
| `captions-only-outline` の泳ぎ | **0.074** | 0.148 |

落ちるのは `vsubject-pause`（100.0% → 95.4%）と `vsubject-tilt`（93.4% → 91.0%）で、
どちらも**被写体が締め出した帯へ入っていく素材**。
**入れた率だけを見ると締め出さないほうが良く見える**が、それは
**縦の窓が広くて 0.119 のずれでも「入っている」と数えられるから**で、
画では高さの 12% ぶん外れている。ここは入れた率ではなくずれと泳ぎで決めた。

### 泳がないことは、正しいことを意味しない

横の手をそのまま当てると `captions-only`（声も被写体も無い・上下に字幕）の泳ぎが
**0.000 / 秒**になる。良い数字に見えるが、中身は**振れ幅も 0.000**——
枠が**画面のいちばん上（0.281 ＝ 窓の半分）に貼り付いて動かない**だけだった。
生の位置は 0.071（＝上の字幕の帯）を指し続けていて、枠は端で止まっている。

**止まる所の近くでは、間違いが止まり方に隠れる。** 同じ穴を素材の側でも踏んだ——
最初 `vsubject-static` の被写体を 0.28 に置いたら、判定が字幕（0.068）を指していても
枠は 0.281 で止まり、**正解とのずれが 0.001 になって満点に見えた。**
置き所を 0.40 へ動かしたら、その場で 100% → **0.0%** に落ちた。
**正解を「動けなくなる所」の近くに置かないこと。**

### 潰すつもりで作った素材が、潰せなかった

`trendOdds` は「背景の階調はまっすぐ」とみなしている。なら**直線で表せない背景**＝
空と地面がくっきり分かれた絵が潰すはず、と思って `vsubject-horizon` を足した。
**潰れなかった**（ずれ 0.023 ・入れた率 100.0%）。しかも横の手でも 0.000 で、
**地平線はむしろ易しくなる。**

理由は、`spatial` を負かしていたのが「階調があること」ではなく
**「隔たりが端へ向かって一本調子に増えること」**だったから。
一本調子の坂では山が必ず端に立つ。段差ではそうならない——
中央値が 2 つの平らな面のどちらかに乗るので、被写体はそのまま浮いたままになる。
**直線を外す手が効くのは坂に対してで、段差は最初から敵ではなかった。**

残ったのは別の形で、段差を直線で外すと**画面のいちばん下の帯に残りが立つ**
（被写体と同じ 0.15〜0.19）。そこは `axisBand` が締め出している側なので、
**潰し素材が当たったのは狙った所ではなく、もう塞いである所**だった。

### 字幕の帯の線（0.15）は、横から持ってきた数字そのまま

横の `rowBand` が上下 15% を落としているので、縦の `axisBand` も同じ 0.15 にした。
**同じ仮定（「字幕は上下にある」）を、同じ数字で、別の場所に当てている。**
振り直してはいない（振るなら字幕の帯の厚みを変えた素材が要る）。

## 読むコマの速さ（2026-09-25・2 回目）

`npm run lab:reframe:decimate`。**焼く・読む・畳む・枠を決めるをブラウザの中で通す**測り方で、
合成コマでは見えないもの（圧縮の粒）を込みで測る。

### 既定は 30fps。**当たるからではなく、振れないから**

1 回目（9/25）に「間引くと落ちる（`motion` で 92.6% 対 97.9%）」と書いた。
2 回目に測り直したら、**その 5.3 ポイントのうち中身があったのは 0.0 ポイントだった。**

まず**測り方に穴があった**。読む時刻をコマの頭（`i / fps`）に置いていたので、
素材の速さの見積もりがほんの少し速いだけで、**列ぜんたいが 1 コマ前へずれる**
（`decode.ts` の `sampleTimes` の注）。直したうえで 7 本並べると:

| | 15fps 読み | 30fps 読み |
| --- | --- | --- |
| 入れた率（7 本の平均） | **96.5%** | **96.5%** |
| 読む＋畳む（13 秒） | 129ms | 234ms |
| コマとメモリ | 195 ・ 6.9MB | 390 ・ 13.7MB |
| `MAX_ANALYSIS_FRAMES` までの尺 | 200 秒 | 100 秒 |

**平均は同じ。** 残るのは振れ幅のほうで、こちらははっきり違う。
中身も速さも変えずに**焼くビットレートだけ 5 通り**振ると（粒は 0.00149〜0.00158 とほぼ動かない）:

| 素材 | 15fps 読み | 30fps 読み |
| --- | --- | --- |
| `motion` | 92.6〜98.4%（**5.7pt**） | 97.9〜98.4%（0.4pt） |
| `subject-decoy` | 92.6〜96.7%（**4.1pt**） | 96.3〜97.9%（1.6pt） |
| `subject-pan` | 0.0pt | 0.4pt |
| `subject-dart` | 0.0pt | 0.0pt |

**1 回目に見た 5.3 ポイントは、間引いた側の当たり外れ（5.7pt）の中に丸ごと入る。**
言えるのは「間引くと落ちる」ではなく「**間引くと、同じ動画を焼き直しただけで答えが動く**」。
ならしは中央値なので、窓に入る標本が半分になると中央値が隣の値へ飛びやすくなり、
その飛びを門（`deadband` / `settle`）が「動き出す / 動かない」へ拡大する。

同じ素材を入れ直したら同じ枠が出てほしいので、**再現性を買って 30fps にした**。
上げ止めているのは 60fps まで読んでも上がらないから（`motion` 97.3% ・ 時間とメモリは倍）。
**素材の速さに合わせる（間引かない）を選ばなかった**のは、それだと 120fps の素材で値段だけが 4 倍になるため。

### ならしの窓を広げる手は取らなかった

標本が足りないなら窓を広げればよい、という手もある（1 回目はそれを勧めていた）。
潰す素材（`subject-dart`＝0.8 秒の寄り道が 2 回）を足して測ると:

| | ならし 1.0 秒 | ならし 2.0 秒 |
| --- | --- | --- |
| 寄り道のあいだ・ならしたあとのずれ | 0.005 | **0.173** |
| 寄り道のあいだ・入れた率 | 46.7% | **13.3%** |
| 8 本の平均 | 96.5% | 95.4% |

**窓より短い動きは、中央値の中で少数派になって消える。**
`motion` 1 本では 92.6% → 97.5% と「戻る」ように見えるが、それは交換で、
しかも**振れ幅は直らない**。

### 「荒れ」を隣り合うコマの差で測ってはいけない

1 回目に「生の位置の荒れ 0.0105 → 0.0065」と書いた数字は、**粒ではなく標本の間隔**を見ていた
（被写体が動いた量そのものなので、間引けば必ず倍になる）。
等速で動く被写体は前後の真ん中に乗るので、**2 階差**を取れば動きが消えて粒だけが残る。
それで測り直すと、ビットレートを 100 倍振っても粒は 0.00149 → 0.00158 しか動かない——
**上の振れ幅は、粒が増えたせいではない。**

## 画面（2026-09-25）

`npm run lab:reframe:demo`。本物の動画を読み、枠の動きを描き、**切り出した縦型をその場で見せる**。
確かめは 55 件（`npm run lab:reframe:uitest`。2026-10-04・2 回目に縦の軸で 28 件足した）で、
素材をその場で WebM に焼いて画面へ食わせる。

### 絵は読み直していない

表紙の画面（`thumbnail`）では「測るコマ（長辺 128）」と「出す絵（実寸）」で**読み込みが 2 本要った**。
こちらは要らない。出口が 1 枚の絵ではなく**枠の列**（`toCropRects`）なので、
**元の `<video>` を横へずらして覗くだけ**で出来上がりになる。
縮めたコマは測るためだけに使い、人が見る絵は元の動画がそのまま持っている。
**出口が「値」なのか「絵」なのかで、画面に要る読み込みの数が変わる。**

ずらして見せているだけなので、検算も「ずらし量が枠と合っているか」だけでは足りない
（向きを間違えても数は合う）。`uitest.mjs` は**縦型の画面を撮って明るさの形を作り**、
元のコマの列（32 列）の上を滑らせていちばん合う左端を探している。
`subject-static` の 6.00 秒で **0.563 対 枠の左端 0.566・相関 0.997**。
ずらしを 0 に戻すと 0.000 になって落ちるところまで確かめてある。

### 間引くと、圧縮を通したときだけ動く

シーン検出の画面は「既定のつまみが 15fps という単位を隠し持っていた」ので、
速いまま渡すと壊れた。こちらのつまみは全部「秒」なので**間引いても動かないはず**で、
合成コマではそのとおりだった（`motion` を 15fps 素材 / 30fps 素材 / 30fps 素材を 15fps へ間引き、
**3 通りとも 99.2%**）。ところが**圧縮を通すと動く**（`motion` で 92.6% 対 97.9%）。

**つまみが秒で書いてあることは「コマの速さに依らない」を意味しない。**
**合成コマでは粒が乗らないので、この穴はコマンドラインでは永久に見えない。**

→ ただし **2026-09-25（2 回目）に測り直したら、この 5.3 ポイントは「落ちた」ではなく
「振れた」だった**（上の「読むコマの速さ」の節）。ここに書いてあった
「ならしを倍にすると戻るのが裏取り」も、**7 本で測ると成り立たない。**
1 本の素材で 5 ポイント動いたのを、読み方の差と読んでいた。

### 目盛りが既定を表せないと、画面だけが黙ってずれる

既定は判定の側（`DEFAULT_REFRAME`）から写している。それでも窓の幅だけ、
**画面は 31.5% で動いていた**——つまみの目盛りが 0.005 きざみで、
既定（81/256 = 0.31640625）が目盛りに乗らなかったため。
**「既定を写す行」を見ても気づけない**（その行は通っている）ので、
目盛りを 1/256 きざみに直したうえで、`uitest.mjs` が**画面が実際に使っている値**を見ている。

### 計画は、生の位置とならしたあとを別々に持つ

画面に「生の位置」と「ならしたあと」を並べて描こうとして、**計画が 1 本しか返していない**ことに気づいた
（`ReframeFrame.target` にはならしたあとが入っていて、注だけが「生の位置」と言っていた）。
枠が遅れているとき、**原因が「生の位置が荒れている」のか「ならしが追い付いていない」のかは、
片方だけでは切り分けられない**ので `raw` を足した。検算も 1 件足してある（23 件）。

## 画面（縦の軸・2026-10-04・2 回目）

同じ画面の「決める軸」で切り替える（横 ・ 16:9 → 9:16 / 縦 ・ 9:16 → 1:1）。
**2 枚に分けなかったのは、判定の側で軸に依らない所が測れていたから**——
枠を決める段は 1 行も書き換えずに乗ったので、画面の側も読み込み・時間軸の絵・
つまみの配線・プレビューの骨格は共通で、入れ替わるのは**どっちの辺を動かすか**だけ。

画面とコマンドラインの突き合わせ（素材を `native` で WebM に焼いて読む・15fps）:

| 素材 | 入れた率（画面 / CLI） | ずれ（画面 / CLI） |
| --- | ---: | ---: |
| `vsubject-static` | 100.0% / 100.0% | 0.051 / 0.051 |
| `vsubject-pause` | 95.9% / 95.4% | 0.052 / 0.052 |
| `vsubject-tilt` | 91.0% / 91.0% | 0.072 / 0.071 |
| `vsubject-cuts` | 93.4% / 93.4% | 0.103 / 0.103 |
| `vsubject-captions` | 100.0% / 100.0% | 0.016 / 0.016 |
| `vsubject-horizon` | 100.0% / 100.0% | 0.023 / 0.023 |

**圧縮を通しても、縦は横より揃う**（ずれの差は最大 0.001。横は焼き直しで数ポイント動いた素材がある）。
`captions-only` の泳ぎも画面 0.047 / CLI 0.047。人が見る絵も撮って確かめた
（`vsubject-pause` の 12 秒で、いちばん合う上端 0.383 対 枠の上端 0.386・相関 0.997）。

### 既定は軸ごとに別なので、軸を替えたらつまみへ写し直す

窓（31.6% / 56.25%）、畳む帯（上下 15% / 全部）、軸の上の帯（全部 / 上下 15%）が軸で違う。
写し直さないと**縦の軸に横の窓 31.6% が残ったまま数字が出る**——壊して確かめたら、
10 件が落ち、`vsubject-captions` は入れた率 100% → **0%**（字幕を指す）になった。
代わりに、つまみを手で回してから軸を往復すると手入れは消える。**既定が食い違ったまま
数字が出るより、消えるほうがましだと決めた。**

### 「軸を替えたら畳み直す」は、既定の違いに隠れていた

畳み直しの条件から「軸が変わったら」を消しても、最初に書いた検査は**素通りした**。
軸を替えると既定が写し直され、畳む帯が 0 ↔ 0.15 と必ず動くので、**帯の違いだけで畳み直しが起きていた。**
いまの既定ではたまたま無害だが、既定が揃った日に**横の判定へ縦の行を渡す**ことになる。
検査は「縦のまま帯を横の既定へ揃えてから軸を替える」形に直し、壊すと落ちることまで確かめた。
**2 つの条件が一緒に動く所では、片方を消した壊し方は、もう片方に救われて見えない。**

### 覗き窓の基準を、自分の答えから取らない

横では出来上がりの高さが決め打ち（320px）で、幅だけを窓の形から決めていたので
`clientHeight` を基準にできた。縦では**高さのほうが窓の形で決まる**ので、
`clientHeight` を基準にすると呼ぶたびに縮む（壊して確かめると 1 回目から 5×5 画素）。
基準は `data-height` から読む（時間軸の絵の `fit()` と同じ形）。

### 縦の素材は、元の画を幅で描くと画面を占領する

元の画は欄の幅いっぱいに描いていた。縦（9:16）では高さが幅の 1.8 倍になり、
**撮った画面で元の画が 1600px 近くまで伸びていた**（数字の確かめは全部通っていた）。
縦長の素材では出来上がりの 2 倍の高さで止めている。**画面は数字だけでなく撮って見ること。**

## 置き方

- `src/columns.ts` — コマを「横の位置ごとの中身」に畳む。**判断を置かない**（手の候補を並べるだけ）。
- `src/reframe.ts` — どの手を使い、いつ枠を動かすかを決める。`summarizeForReframe()` が入口。
- `src/selftest.ts` — 合成データでの検算（26 件）。素材は作らないので数秒で終わる。
- `src/demo.ts` / `index.html` / `src/style.css` — 画面。**判断は置かない。**
  読み込み（`scene-cut/src/decode.ts`）と見た目（`auto-cut/src/style.css`）は借りている。
- `score.mjs` — 採点。**`bench.mjs` と `uitest.mjs` が同じ関数を呼ぶ**ために切り出してある。
- `probe.mjs` / `bench.mjs` / `uitest.mjs` — 手を選ぶ表と、効きの表と、画面の確かめ。
- `gate-probe.mjs` — **門の形の表**（焼き直しで枠がどれだけばらけるか）。
- `decimate-probe.mjs` / `testkit/decimate.ts` — 読むコマの速さの表。`gate-probe.mjs` も同じ口を使う。
  **`bench.mjs` と分けてある**のは、あちらが合成コマ（ブラウザ不要・数秒）なのに対し、
  こちらはブラウザで焼いてから読む（圧縮の粒が要る）ため。採点は `score.mjs` で同じ。

本体（`src/`）へはまだ繋いでいない。出口は `toCropRects()` で、
`{ time, x, width }` の列を返す（`x` は左端・0〜1）。
