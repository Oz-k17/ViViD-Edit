# export-cost — 書き出しの費用（どこで時間を使っているか）

書き出し（`src/engine/offline-export.ts`）は 1 コマずつ
「デコードを待つ → 描く → エンコードを待つ」を回している。遅いのは分かっていたが、
**どこが遅いのかは測られていなかった**ので、まずそこを測るための試作。

触る画面は無い。出口はコマンドだけ。

```
npm run lab:test           # 数え上げ・待ち行列・音の置き方の検算（ブラウザ不要・数秒）
npm run lab:export         # 映像の実測（ブラウザ・playwright が無ければ数え上げだけ出して終わる）
npm run lab:export:audio   # 音の実測（同上）
npm run lab:export:range   # 素材の要る範囲だけを起こす（同上・本物の WebM / Opus を焼いて測る）

LAB_EX_DEPTHS=0,8,16 npm run lab:export        # 重ねる枚数を振る（0 は直列＝いまの本体）
LAB_AU_SECONDS=13,26,52 npm run lab:export:audio  # 尺を振る
LAB_AU_WINDOW=5 npm run lab:export:audio          # 窓の幅（秒）
LAB_RG_ASSET=120 npm run lab:export:range         # 焼く素材の尺（秒）
```

## 2 段に分けてある

| | 何を見るか | 要るもの |
| --- | --- | --- |
| 数え上げ（`src/plan.ts`） | 何枚デコードするか・何回開き直すか・歩幅はいくつか | 何も要らない |
| 実測（`testkit/measure.ts`） | デコード・描画・エンコードに何ミリ秒かかるか | ブラウザ |

重ねる待ち行列（`src/pipeline.ts`）も時計にも DOM にも触らないので、
「何枚まで抱えるか・順番が狂わないか・失敗が消えないか」は `npm run lab:test` で回る。

**数えられるものを測るのは順番が逆**なので、先に数え上げを出してから、
残ったぶんだけをブラウザで測る。数え上げのほうは端末にも素材にも依らないので、
そのまま記録として持ち越せる。

## 測って分かったこと（2026-09-26・1024×576・390 コマ・5 回の中央値）

### 1. 遅いのはデコード。エンコードではない

| 段 | 合計 ms | 1 コマ ms | 取り分 |
| --- | ---: | ---: | ---: |
| decode | 2519 | 6.46 | **86.4%** |
| draw | 13 | 0.03 | 0.4% |
| encode | 384 | 0.98 | 13.2% |

壁時計 2.92s ＝ **実時間の 4.46 倍速**。

描く段が 0.4% しか無いのは、この試作が**素の 1 枚を貼るだけ**だから。
本物はテロップ・エフェクト・トランジションを重ねるのでここは増えるが、
**増えてもデコードの側は減らない**ので、下の話は変わらない。

### 2. 「取り分 86%」を「直せば 7.3 倍」と読んではいけない

直列を仮定した上限（`cost.ts` の `projectSpeedup`）では、
デコードをタダにすれば **7.34 倍**と出る。ところが実際にデコードを 2.9 倍速くしても、
**壁時計は 1.67 倍しか縮まなかった**。

| やり方 | 壁時計 s | decode ms | encode ms | 前と比べ |
| --- | ---: | ---: | ---: | ---: |
| `at-timestamps`（いまの本体） | 2.92 | 2519 | 384 | 1.00 倍 |
| `pool`（canvas を使い回す） | 2.43 | 1756 | 658 | 1.20 倍 |
| `sequential`（順に読む） | 1.90 | 1173 | 713 | 1.54 倍 |
| `sequential-pool`（両方） | 1.75 | 878 | 855 | **1.67 倍** |

デコードが 2519 → 878ms に落ちたぶん、**エンコードが 384 → 855ms に増えている**。
段ごとの時計が測っているのは「その段が重いか」ではなく
**「そこで待たされたか」**で、`videoSource.add()` はエンコーダが詰まっていれば返ってこない。
片方を速くすると待ちがもう片方へ移るだけなので、**直列を仮定した上限は当てにならない。**

### 3. 効くのは「順に読む」こと。ただし飛ばして読むときは逆に損

mediabunny の `CanvasSink` には 2 つの読み方があり、本体は飛び石のほう
（`canvasesAtTimestamps`）だけを使っている。docs には
「**順に読むなら `canvases()` のほうが良い**（先読みが効く）」と書いてある。

| 再生速度 | 歩幅（素材コマ） | 順に読む形 |
| ---: | ---: | ---: |
| 1 倍 | 0.5 | **1.80 倍** |
| 2 倍 | 1.0 | 1.30 倍 |
| 3 倍 | 1.5 | 1.05 倍 |
| 4 倍 | 2.0 | **0.83 倍（損）** |

飛ばして読むぶんには、要らないコマまで canvas へ起こす手間がそのまま無駄になる。
**「順に読むほうが速い」は、順に読むときだけの話だった。**

`src/plan.ts` の `decodeShape()` は、この歩幅を**時計を使わずに**出して
どちらの読み方が向くかを返す。線は互角だった 1.5 ではなく **1.25** に置いてある
（互角で乗り換えても得が無いこと、そして境目ちょうどに線を置くと
浮動小数の丸めが答えを決めることの 2 つ。後者は同じ日に一度踏んだ）。

### 4. 1 本の素材を割ると遅くなる。出来上がりは 1 ビットも変わらないのに

本体はデコーダを**クリップごと**に開く。1 本の動画を 20 個に割ったタイムラインでは、
同じファイルを 20 回開き直して、20 回鍵コマから読み直す。

| 割る本数 | やり方 | 壁時計 s | 開く回数 | 開く ms | decode ms |
| ---: | --- | ---: | ---: | ---: | ---: |
| 1 本 | `at-timestamps` | 3.08 | 1 | 4 | 2502 |
| 5 本 | `at-timestamps` | 2.86 | 5 | 18 | 2543 |
| 20 本 | `at-timestamps` | 3.18 | 20 | 74 | 2931 |
| 20 本 | `shared`（素材ごとに 1 本） | 2.99 | 1 | 5 | 2305 |

**代価は「開く時間」には出ない。** 開く時間は 74ms（壁時計の 2%）でしかなく、
増えているのは**開いた直後のデコード**のほう（2502 → 2931ms）。
`開く ms` だけを見て「大したことない」と読むのが落とし穴で、
数え上げの `redundantOpens` が 19 と出ているのに実測が 1.03 倍しか動かないのも同じ理由。

### 5. 出口 — `auto`

3 つを、注文の形を見て組み合わせたのが `auto`。
**素材ごとに 1 本開き、canvas を使い回し、歩幅が狭ければ順に読む。**

| | `at-timestamps` | `auto` |
| --- | ---: | ---: |
| 1 本・等速 | 3.08s | **1.72s（1.79 倍）** |
| 20 本に割る | 3.18s | **1.82s（1.75 倍）** |
| 4 倍速 | 0.85s | **0.74s（1.15 倍）** |

4 倍速で `sequential-pool` が 0.83 倍と負ける場面でも、`auto` は 1.15 倍で通る。
**どちらが速いかを選べる形にしたので、潰し素材でも負けない。**

### 6. デコードとエンコードを重ねても、速くならなかった（2026-09-26・2 回目）

2. の「片方を速くすると待ちがもう片方へ移るだけ」から、**重ねれば両方ぶん縮むはず**と
書いて終わっていた。作って測ったら、**縮まなかった。**

`add()` が返す約束を `encodeDepth` 枚まで未完了のまま先へ進む形にしてある
（`src/pipeline.ts` の `InFlightQueue`）。0 枚がいまの本体と同じ直列。

| やり方 | 枚数 | 輪 s | 仕上げ s | 合計 s | decode ms | 投げ ms | 待ち ms | 振れ幅 | 前と比べ |
| --- | ---: | ---: | ---: | ---: | ---: | ---: | ---: | ---: | ---: |
| `at-timestamps` | 0 | 2.88 | 0.07 | 2.95 | 2185 | 622 | 64 | 3.7% | 1.00 倍 |
| `at-timestamps` | 1 | 2.67 | 0.03 | 2.70 | 2211 | 438 | 9 | 3.9% | 1.09 倍 |
| `at-timestamps` | 4 | 2.67 | 0.03 | 2.70 | 2155 | 497 | 10 | 3.1% | 1.09 倍 |
| `auto` | 0 | 2.06 | 0.06 | **2.12** | 813 | 624 | 615 | 2.9% | 1.39 倍 |
| `auto` | 1 | 1.52 | 0.58 | **2.11** | 824 | 621 | 71 | 10.4% | 1.40 倍 |
| `auto` | 2 | 1.58 | 0.55 | **2.13** | 795 | 733 | 42 | 2.1% | 1.38 倍 |
| `auto` | 4 | 1.59 | 0.48 | **2.06** | 937 | 632 | 10 | 9.3% | 1.43 倍 |

**出口にしたい `auto` の上では 1.00〜1.03 倍**、つまり何も起きていない（振れ幅 2〜10%）。
枚数を 8・16 まで増やしても合計 2.05〜2.21s で変わらない。
`at-timestamps` の側だけ 1.08〜1.09 倍と揃って出るが、そちらは 9/26（1 回目）の時点で
`auto` に置き換えるべきと分かっている形なので、**重ねる価値がある場所ではない。**

**既定は 0 枚（直列）のまま。** 道具としては残してあるので、
ハードウェアのエンコーダがある端末で測り直す価値はある（下の注を参照）。

#### なぜ縮まないのか — `encode` の取り分の半分以上は「待ち」ではなかった

| 読み方 | 倍率 |
| --- | ---: |
| `encode` の取り分をそのまま重ねる（素朴） | 1.76 倍 |
| **待っていた時間だけ**重なる | 1.41 倍 |
| 実測（いちばん良かった枚数） | **1.03 倍** |

`CanvasSource.add()` は、呼んだその場で `new VideoFrame(canvas)` を作り、
符号化器へ渡すところまでを**同期で**通す。待ちが入るのはその後ろだけ。
つまり `encode` の 1239ms（`auto`・0 枚）は **投げ 624ms ＋ 待ち 615ms** の 2 つで、
**約束を後ろへ回して消せるのは後者だけ**。前者は 1 ミリ秒も減らない。

`cost.ts` の `projectOverlap` は段の取り分をそのまま「重ねれば消える量」として扱うので、
**ここを 1.76 倍と読み違える。** 同じ日に `projectOverlapMs` を足して、
**重ねて消せるぶんだけ**を渡す形にした。それでも 1.41 倍と出て実測は 1.03 倍なので、
**見積もりは 2 段階に直してもまだ大きい。**

残りの説明は「消えた待ちが仕上げへ移っただけ」。`auto` の 1 枚は
輪が 2.06 → 1.52s へ縮むが、仕上げが 0.06 → 0.58s へ増えて**合計は動かない**。
符号化器は追い付いていないので、輪の中で払わなかったぶんを最後に払う。
**輪だけを見ていると「1.36 倍速くなった」と書いてしまう。**

#### 測り方: 交互に回さないと、振れ幅を差として読む

最初は他の節と同じく**設定ごとに固めて** 3 回ずつ測った。その表では
`auto` の 2 枚が **1.55 倍**と出ていた。**設定を交互に回したら 1.02 倍になった。**

固めて測ると、その間のページの温まり方・ほかのプロセス・ゴミ集めの波が
**そのまま設定の差に化ける**。1 回捨てても、ページごと 2 回空回ししても消えない
（どちらも「塊の中」を揃えるだけなので、塊どうしの差は残る）。
効きが 5% 前後のときは**塊を作らない**しかない。`bench.mjs` の `runInterleaved` が
1 周ごとに順番をひっくり返しながら回すのはそのため（先頭はいつも少し冷えているので、
行き帰りで打ち消す）。**この節だけ他と測り方が違うのは、この節だけ差が小さいから。**

#### 出来上がりの照合は、作り直した

重ねると絵が入れ替わる・順番が狂う・コマが落ちるのが怖い。ところが
**それまでの照合では捕まえられない**——`digests` は**エンコードへ渡す前の canvas** を
見ているので、その後ろで何が起きても同じ値が並ぶ。なので
**出来上がった WebM を読み直して**突き合わせる形を足した（`measure.ts` の `verify`）。

結果は**升目の開きの最大が 0.0000 / 255**、つまり 1・2・4 枚のどれでも
直列と**ビット単位で同じ**ものが出る。順番が狂わない理由は mediabunny の中を読んで
確かめてあるが（`src/pipeline.ts` の注）、**中を読んだ根拠と出口で測った根拠は別物**なので、
ここは後者を置いた。

**畳み方を 2 回間違えた。** 1 つ目は全コマを 1 つの平均にしたこと
（わざと 1 コマずらした相手が 0.71 / 255 で素通り）。2 つ目はコマごとに分けたあとも
**升目の平均**を見たことで、こちらも 3 / 195 コマしか立たない。
場面の中の動きは画面のごく一部なので、升目 256 個で割ると平均の中に消える。
**升目ごとの最大**で見ると 128 / 195 コマが立ち、canvas 側の指紋（129 / 195）とほぼ並ぶ。
**「検査を書いたらわざと壊して落ちることまで確かめる」を守ったから気づけた。**

### 7. 音の先払いは、時間ではなくメモリだった（2026-09-26・3 回目）

本体は**映像の 1 コマ目を描く前に**タイムライン全体の音を 1 本の `AudioBuffer` へ混ぜる
（`renderAudioMix`）。ここは 9/26 の 1・2 回目では 1 秒も測っていなかった。

先払いしているのは 2 つだけ——**素材を起こす**のと**混ぜる**の。
切り出し・出力へ渡す・仕上げは、映像の輪と一緒に進む（`pushAudioUpTo` がコマごとに呼ばれる）。

| 尺 | やり方 | 起こす | 混ぜる | 切り出す | 渡す | 仕上げ | **先払い** | 抱える山 |
| ---: | --- | ---: | ---: | ---: | ---: | ---: | ---: | ---: |
| 13 秒 | 一括（いまの本体） | 8 | 9 | 3 | 6 | 101 | **17ms** | 4.8MB |
| 13 秒 | 窓 1 秒 | 9 | 14 | 0 | 6 | 92 | 23ms | **0.4MB** |
| 52 秒 | 一括 | 10 | 44 | 13 | 26 | 403 | **54ms** | 19.0MB |
| 52 秒 | 窓 1 秒 | 8 | 55 | 0 | 26 | 342 | 63ms | **0.4MB** |

段ごとの振れ幅は **7〜21%** ある（1 回が 100ms 台なので、ゴミ集めの波 1 つで順位が動く）。
**桁と順位だけを読むこと。** 走らせ直すと「混ぜる」は 9〜14ms のあいだで動く。

**時間のほうは効かない。** 先払いは 1 秒あたり **1.04ms** で、10 分のタイムラインで 0.6 秒、
1 時間で 3.8 秒。映像の側は 13 秒で 1.75〜2.92 秒（＝ 1 秒あたり 135〜225ms）なので、
**音は映像の 100 分の 1 以下**。「長尺で効くのはむしろ音のほうかもしれない」は外れだった。

**効くのはメモリのほう。** 入れ物は尺だけで決まる（48000 × 2ch × 4 バイト ＝ **1 秒 384KB**）。

| 尺 | ミックス | 複製の回数 | 一括の山 | 窓 1 秒の山 | 一括 ÷ 窓 |
| ---: | ---: | ---: | ---: | ---: | ---: |
| 13 秒 | 4.8MB | 13 | 9.9MB | 5.1MB | 2 倍 |
| 60 秒 | 22.0MB | 60 | 27.1MB | 5.1MB | 5 倍 |
| 10 分 | 219.7MB | 600 | 224.9MB | 5.1MB | 44 倍 |
| 1 時間 | 1318.4MB | 3600 | 1323.5MB | 5.1MB | **258 倍** |

#### 窓に割ると、波は 1 標本も変わらない。混ぜる時間は窓の幅で決まる

`src/audio-mix.ts` は、置き方を**一括も窓割りも同じ 1 本の道**から出す（`windowSounds`）。
窓を尺いっぱいに取れば本体の一括ミックスそのままなので、**差が出たらそれは窓のせい**と言える。

| 尺 | やり方 | 混ぜる | 切り出す | 1 秒あたり | 抱える山 | 混ぜた回数 |
| ---: | --- | ---: | ---: | ---: | ---: | ---: |
| 52 秒 | 一括 | 44ms | 12ms | 1.08ms | 19.0MB | 1 |
| 52 秒 | 窓 1 秒 | 55ms | 0 | 1.05ms | 0.4MB | 52 |
| 52 秒 | 窓 5 秒 | 41ms | 0 | **0.78ms** | 1.8MB | 14 |

**窓 5 秒は、時間もメモリも一括より良い。** `OfflineAudioContext` を作る手間は窓の数に比例するので、
窓を狭くしすぎると混ぜる時間で損をする（窓 1 秒は一括と互角まで落ちる）。
一方で**切り出し（`sliceAudio`）は窓割りでは 1 回も要らない**——混ざった窓をそのまま渡せるので。
ただし本体が 1 秒刻みで渡しているのは多重化のバッファを膨らませないためなので、
窓を広げるなら「渡す塊も広がる」か「複製が 1 枚要る」かのどちらかになる。

渡した波の照合（区画 512 標本・符号つき平均と絶対値の最大）は、
**窓 0.37 / 1 / 5 秒・5 つに割った素材・44.1kHz の素材のどれでも開き 0**（最大 4.5e-8）。
わざと素材内の位置を進めない窓割り（`windowed-broken`）は 1219 区画のうち 1126 区画で落ちる。

#### 窓に割って本当に難しいのは、折れ線の**出口**だった

素材内の位置を進める（`offset += (a - from) * speed`）のは分かりやすい。
検算が捕まえたのはもう片方で、**窓の外にある節を捨てるだけでは、窓の中でフェードが止まる**。
最後の節から先は値が保持されるので、フェードアウトの途中で窓が切れると
そこから先が下がらないまま鳴り続ける（食い違い **0.53**）。
`windowSounds` は窓の出口にも節を打っている。

#### 見つけた穴: 利得の初期値 1.0 が、クリップの頭で 1 標本だけ漏れる

窓に割った波が一括と違うと出たので調べたら、**犯人は窓ではなかった。**

本体の `place()` は `gain.gain.setValueAtTime(...)` だけで始めるが、`GainNode` の初期値は **1.0**。
その節が音源の開始より **1 標本でも後ろに丸められると、そこだけ利得 1.0 で鳴る。**
実測では、クリップの頭ちょうどの 1 標本が**素材の生の値そのまま**で出た
（7.80 秒で -0.02895 ＝ 素材の値、両隣は 0）。
**音量 0.1 のクリップでも、フェードインの途中でも、その 1 標本だけは素通りする。**

窓に割ると節の時刻が窓の頭からの相対秒になるので**丸めの残りが変わり、漏れる場所も変わる**。
だから「窓に割ると波が違う」に見えた。`gain.gain.value` を先に入れれば、
どちらへ丸めても 1.0 は出てこない（`testkit/audio.ts` の `placeInto`）。
**本体（`src/engine/offline-export.ts`）にも同じ穴がある。** 1 標本なので気付きにくいが、
クリップの頭が並ぶタイムラインではその数だけ出る。`lab:export:audio` の照合に
`leakDefaultGain`（本体と同じ書き方）を残してあるので、直したかどうかはそこで測れる。

#### 起こす素材は「使う秒」では決まらない。ここは窓に割っても減らない

| 形 | 使う秒 | 起こす秒 | 起こすバイト |
| --- | ---: | ---: | ---: |
| 13 秒の素材を丸ごと | 13s | 13s | 4.8MB |
| 10 分の素材から 10 秒 | 10s | 600s | 219.7MB |
| 1 時間の素材から 10 秒 | 10s | 3600s | **1318.4MB** |

`decodeAssetAudio` は**素材まるごと**を起こして `decoded` に持ち続ける。
**窓に割って減るのはミックスの側だけ**で、こちらは 1 バイトも減らない
（1 時間の素材から 10 秒を切り出すタイムラインでは、窓割りの効きは 1.00 倍）。
**長尺で先に当たる壁はこちら**で、要るのは「素材の要る範囲だけを起こす」ほう。

#### 測り方で踏んだ穴

- **素材 13 秒のまま尺だけ 52 秒に伸ばしていた。** 13 秒より後ろの窓には置く音が無い
  （素材の端を越えるので）ので、**残り 39 秒は無音を混ぜていた。**
  尺を振ったつもりで「無音の割合」を振っていたことになる。
  いまは尺を埋めるのに要る本数へ自動で割っている（`audio.mjs` の `piecesFor`）。
- **指紋を「渡した塊ごと」に切っていた。** 窓の幅を変えると塊の数が変わるので、
  比べる相手と長さが揃わず「違う」以前に比べられない。区画は**全体を通した標本の番号**で切る。
- **段ごとの時間は、段ごとに中央値を取る。** 「合計が中央値だった回」を 1 回選ぶ形だと、
  10ms 台の段はその回の当たり外れをそのまま持ってくる（混ぜる時間が 8〜32ms に見えた）。

### 8. 素材の要る範囲だけを起こす（2026-09-30）

7. で「長尺の本命の壁は素材まるごとのデコード」と分かったので、そこを測った。
組み立ては `src/audio-ranges.ts`（判断だけ・DOM も WebAudio も mediabunny も触らない）、
実測は `testkit/audio-range.ts`（**本物の WebM / Opus を 1 回焼いてから**
`AudioBufferSink.buffers(from, to)` で範囲読みする。本体の `decodeAssetAudio` と同じ経路）。

**WAV で測らないのが要点。** WAV は PCM なのでバイトを切れば範囲が取れてしまい、
頭出しも packet の丸めもデコーダの立ち上げも出てこない。本体が食うのは配信の録画なので、焼く。

#### 起こす秒と抱えるバイトは、素材の尺 ÷ 使う秒のぶんだけ減る

| 形 | 使う秒 | 丸ごと | 範囲 | 区間 | 丸ごと ÷ 範囲 |
| --- | ---: | ---: | ---: | ---: | ---: |
| 13 秒の素材を丸ごと | 13s | 4.8MB | 4.8MB | 1 本 | 1.0 倍 |
| 10 分の素材から 10 秒 | 10s | 219.7MB | 3.8MB | 1 本 | 58.5 倍 |
| 1 時間の素材から 10 秒 | 10s | 1318.4MB | **3.8MB** | 1 本 | **351 倍** |
| 1 時間の素材から 5 分 | 300s | 1318.4MB | 110.0MB | 1 本 | 12.0 倍 |
| ジェットカット・残す 1/4（10 分） | 150s | 219.7MB | 68.6MB | 75 本 | 3.2 倍 |
| ジェットカット・残す 1/4（1 時間） | 900s | 1318.4MB | 411.9MB | 450 本 | 3.2 倍 |

実測（60 秒の WebM / Opus・交互に回した中央値）:

| 形 | やり方 | 起こす | 起こす秒 | 抱える | 区間 |
| --- | --- | ---: | ---: | ---: | ---: |
| 素材の中を順に 13 秒 | 丸ごと | 636ms | 60.0s | 11.0MB | 1 本 |
| 素材の中を順に 13 秒 | **範囲** | **135ms** | 13.1s | **2.4MB** | 1 本 |
| ジェットカット・残す 1/4 | 丸ごと | 613ms | 60.0s | 11.0MB | 1 本 |
| ジェットカット・残す 1/4 | **範囲** | **253ms** | 19.9s | **3.6MB** | 8 本 |

混ざる波は**丸ごとと同じ**（4 通りの形で違う区画 0 / 1219〜2813・最大の開き 5.96e-8）。

**得の大きさは「素材の尺 ÷ 使う秒」で決まる。** ジェットカットした形は
使う秒そのものが素材の 2〜4 分の 1 しかないので、**得も 2〜4 倍で頭打ち**。
1 時間の素材から 10 秒という形（配信から 1 か所だけ切る）がいちばん効く。

#### のりしろが要る理由は「覆いが足りない」ではなく「デコーダが温まっていない」

見立ては逆だった。「手前はデコーダが packet の頭からしか始められないので勝手に付く。
要るのは後ろ側」と書いて始めたが、**測ったら手前がいちばん足りなかった。**

| 助走 | 違う区画 | 最大の開き | 1 区間あたり冷えていた長さ | 要る助走 |
| ---: | ---: | ---: | ---: | ---: |
| 0s | 167 / 1500 | 4.6e-2 | 223ms | 223ms |
| 0.05s | 129 / 1500 | 4.8e-3 | 172ms | 222ms |
| 0.1s | 103 / 1500 | 1.5e-3 | 137ms | 237ms |
| 0.2s | 11 / 1500 | 6.1e-5 | 15ms | 215ms |
| 0.3s | **0** / 1500 | 1.0e-6 | 0ms | — |
| 0.5s | **0** / 1500 | 1.5e-8 | 0ms | — |

この表は**2 回走らせても 1 標本も動かない**（波は種で固定してあり、復号も決定的）。
時間のほうは 20〜35% 振れるが、こちらは振れない量として読める。

**覆いは足りている。** 要求した境目からの広がりは 3.5〜13.5ms しかなく、
欲しい標本は全部入っている。それでも**区間の頭から 0.22 秒あたりまで値が違う**。
Opus は前の packet に重ねて復号するので、**途中から始めた先頭のしばらくは本来の値にならない。**
助走を伸ばすと、違う区画の秒がちょうどそのぶん減る——**4 通りが同じ 0.22 秒を指した**ので、
これは偶然ではなく「助走の長さ」という 1 つの量。既定は 0.5 秒（その 2.1 倍）。

だから**のりしろは前後で意味が違う。** 前は「捨てるつもりで起こす秒」、後ろは
「覆いの余裕」。対称にすると後ろも助走ぶん太るだけで、1 山 2 秒の素材では
取り分が 1.27 倍から 1.50 倍へ増える。**後ろは実測では 0 でも波が同じ**だったが、
48kHz でない素材と速さの丸めを試していないので 0.05 秒残してある（2 秒の山で 2.5%）。

#### 畳む幅は、測った釣り合いから決まる

区間ごとに頭出しとデコーダの立ち上げが要るので、隙間が狭いうちは畳むほうが速い。
どこで釣り合うかは、**区間の数と起こす秒を別々に動かして**当てる
（同じ形で残す割合だけ振ると 2 つが一緒に動くので分けられない）。

| 形 | 区間 | 起こす秒 | 起こす ms |
| --- | ---: | ---: | ---: |
| 1 山 2 秒・残す 1/4 | 8 本 | 19.9s | 278 |
| 1 山 2 秒・残す 1/2 | 15 本 | 37.8s | 472 |
| 1 山 1 秒・残す 1/8 | 8 本 | 11.9s | 187 |
| 1 山 0.5 秒・残す 1/8 | 15 本 | 15.3s | 271 |
| 1 山 0.5 秒・残す 1/4 | 30 本 | 31.1s | 513 |
| 1 山 2 秒・残す 4/5（畳まれて 1 本） | 1 本 | 59.6s | 549 |

最小二乗で当てると **1 秒あたり 9.2〜11.4ms ＋ 1 区間あたり 8.1ms**（3 回走らせた幅）。
隙間 G の 2 本を畳むと `9〜11 × G` を払って `8.1` を省くので、
**釣り合うのは G ＝ 0.7〜0.9 秒**。既定の畳む幅 1 秒は、そのすぐ上に置いてある。

**畳む幅だけを振っても計画は動かない**（1 山 2 秒・残す 1/4 の隙間は必ず 6 秒なので、
0s と 1s と 5s は同じ区間になる）。同じ計画どうしで 20〜35% 入れ替わるので、
**この測りでは 1.35 倍未満の差は読めない**。だから 6 点まとめて当てている。

#### いちばん派手に外れるのは「区間の頭ぶんを引き忘れる」

範囲だけ起こすと、出来た `AudioBuffer` の先頭は**素材の先頭ではない**。
`source.start(startAt, offset, …)` の `offset` は素材内の絶対秒なので、
区間の頭ぶん引かないと**その差だけ先を鳴らす**。わざとそうした相手で測ると
**1500 区画のうち 1313 が違う（最大の開き 4.46e-1）。**

9/26（3 回目）の窓割りで踏んだ「素材内の位置を進め忘れる」と**符号が逆の同じ穴**で、
しかもこちらは 1 本ぶんまるごと別の場所を鳴らすので、もっと派手に外れる。
なので置き換えは `offsetInParts` の 1 か所に閉じ込めて、
**載らなかった置き方は黙って 0 にせず null を返す**（0 は無音ではなく素材の頭なので、
耳でも指紋でも「鳴っている」に見えてしまう）。区間を両側から 0.5 秒削った相手では、
8 本の置き方が 8 本とも「載らない」に数えられる。

#### 数えるだけで分かったこと 2 つ

- **消したクリップの素材は、範囲の形なら 1 バイトも起こさない。**
  本体の `renderAudioMix` は「音のあるクリップ」の素材を全部起こしてから、
  置く段で `muted` を落とす（起こす側に `muted` の条件が無い）。
  範囲は鳴る音から組むので、消したクリップだけが使う素材は計画に出てこない。
- **ループは範囲では受けない。** `loopEnd` は起こしたものの末尾になるので、
  素材の端までを 1 本で持っていない区間では折り返し先が変わる。
  ループする置き方は `offsetInParts` が null を返し、丸ごと起こす道へ落とす。
  ループで `sourceIn` が素材の終わり際にある形（本体の `loopStart` が手前へ動く）も、
  数えるのをやめて素材ぜんたいを返す。

#### 測ってみて問題が出なかったところ

- **最初の buffer の時刻は 0.0000s だった。** 本体の `decodeAssetAudio` は
  返ってきた buffer の `timestamp` を捨てて順に繋いでいるので、
  最初の時刻が 0 でない素材では丸ごとの側の t=0 がずれる。WebM / Opus では出なかったが、
  **範囲の側は時刻を使っている**（要求より手前から出てくるので使わざるを得ない）ため、
  ここが 0 でない素材では**範囲のほうが正しい**という向きになる。

## 数字を読むときの注意

- **ミリ秒そのものは持ち越せない。** 確認用のブラウザには GPU が無い
  （`browser.mjs` の swiftshader）ので、VP8/VP9 は丸ごとソフトウェアで回る。
  本物の端末にはハードウェアのエンコーダが付くので、**エンコードの側はもっと軽い**はず。
  その向きだと「デコードが支配する」はさらに強くなる。
- **1 回目は捨てる。** 同じ設定でも 1 回目だけ 1.8 倍遅い（1.97s 対 1.08s）。
  それも設定ごとに 1 回捨てるだけでは足りず、**ページ全体で 2 回空回し**してから入っている。
  入れる前は振れ幅が 75% あり、`pool` の効きが 1.68 倍に見えていた（実際は 1.23 倍）。
- **小さい絵では測れない。** 512×288 では 4 つのやり方が 1.17〜1.29 倍と団子になり、
  振れ幅（18〜30%）の中に埋まる。1024×576 なら振れ幅 7〜13% に対して
  1.00 / 1.20 / 1.54 / 1.67 と順に並ぶ。既定を `scale=8` にしてあるのはそのため。

## 本体へ持っていくとき

`src/plan.ts` の `decodeShape()` と `summarizePlan()` だけが要る部品で、
どちらも DOM にも WebCodecs にも触らない。`testkit/measure.ts` のほうは
**測るための作り**で、本体の輪の代わりにはならない（音もトランジションも入っていない）。

`src/pipeline.ts` の `InFlightQueue` も DOM にも WebCodecs にも触らないが、
**持っていく理由はいまのところ無い**（上の 6. のとおり効かなかった）。

まだ試していないこと:

- **範囲読みを本体へ入れるとき。** 要るのは `src/audio-ranges.ts`
  （`planAssetDecodes` / `offsetInParts`）だけで、DOM にも WebAudio にも mediabunny にも触らない。
  本体側で要る直しは 3 つ: `decodeAssetAudio` が範囲を受け取れること、
  起こしたものを「素材 1 本」ではなく**区間の並び**として持つこと、
  `place()` に渡す `offset` を区間の座標へ移すこと。
  **ループと、範囲に載らなかった置き方は丸ごと起こす道へ落とす**のを忘れないこと。
- **`add()` の同期の手間（投げ 624ms・全体の 29%）を減らす。** 今回いちばんの収穫で、
  ここは**どの段の時計にも単独では出ていなかった**（`encode` の中に紛れていた）。
  中身は `new VideoFrame(canvas)`＝1024×576×4 バイトの複製を 390 回。
  canvas を経由しない渡し方（`VideoSampleSource` に自前の `VideoSample` を渡す、
  デコード結果をそのまま回す）があるなら、そちらのほうが筋がよさそう。
- **`poolSize` の枠の数。** 2 と 4 しか試していない。
- **本物の解像度（1920×1080）と、H.264 のハードウェアエンコーダ。** ここでは測れない。
- **素材の要る範囲だけを起こす。** 上の 7. のとおり、長尺で先に当たる壁は
  ミックスの入れ物ではなく**素材まるごとのデコード**のほう（1 時間で 1.3GB）。
  mediabunny の `AudioBufferSink` は範囲を指定して読めるので、
  「クリップが使う範囲＋のりしろ」だけを起こす形が測れるはず。
- **窓割りを入れるかどうか。** 波は 1 標本も変わらないと確かめた（上の 7.）。
  入れるなら窓は **5 秒あたり**（1 秒だと `OfflineAudioContext` を作る手間で損をする）。
  ただし**時間の得はほぼ無い**（先払いは 1 秒あたり 1.04ms）ので、
  理由はメモリだけ。1 時間で 1.3GB → 5MB。
- **音のトランジション・ダッキングを入れた状態で測る。** いまの `testkit/audio.ts` は
  クリップとフェードと引き延ばしまで。エフェクトが増えると混ぜる側の取り分が増える。
- **ハードウェアのエンコーダがある端末で、重ねる形を測り直す。** ここでは
  デコードもエンコードもソフトウェアで同じ 4 芯を取り合っているので、
  重ねても取り合いに化けるだけという読み方ができる。エンコードが別の回路へ逃げる端末なら
  話が変わる可能性はある。**向きは分かるが桁は分からない**のは 9/26（1 回目）と同じ。
