# lab — 試作置き場

本体（`src/`）に入れる前に、単体で動かして確かめるための場所です。

- 本体のビルド（`npm run build` / `npm run bundle`）からは完全に切り離してあります。
  ここが壊れても配布物には影響しません。
- 各試作は「判断する純粋な関数」と「見せる画面」を分けて書いています。
  本体へ持っていくときに要るのは前者だけです。
- 判断する部分を DOM から切り離しておくと、Node が `.ts` をそのまま実行できるので、
  テストがブラウザ無しで回ります（`npm run lab:test`）。ここは以降も守ってください。
- `playwright` はリポジトリの依存には入れていません（本体の配布物とは関係が無いので）。
  グローバルに入っていれば `lab:uitest` が借りて使い、無ければ飛ばします。

| 試作 | 中身 | 動かし方 |
| --- | --- | --- |
| [`auto-cut/`](./auto-cut/) | 無音カット（ジェットカット）とオートダッキング、波形表示 | `npm run lab` |
| [`scene-cut/`](./scene-cut/) | シーン検出（カットの切り替わりを見つけて割る） | `npm run lab:scene:demo` |
| [`beat/`](./beat/) | 拍の検出（テンポと、拍が来る秒） | `npm run lab:beat:demo` |
| [`thumbnail/`](./thumbnail/) | 表紙（サムネイル）候補の自動抽出 | `npm run lab:thumb` |
| [`reframe/`](./reframe/) | 自動リフレーム（縦型へ切り出す窓を被写体に合わせて動かす） | `npm run lab:reframe` |
| [`export-cost/`](./export-cost/) | 書き出しの費用（映像も音も、どこで時間とメモリを使っているか） | `npm run lab:export` |
| [`keyframe/`](./keyframe/) | 時間で変化する値（キーフレーム）の持ち方 | `npm run lab:keyframe:demo` |
| [`project-pack/`](./project-pack/) | プロジェクトを素材ごと 1 ファイルにまとめて持ち出す | `npm run lab:pack` |

`export-cost` は**触る画面を持たない**（`index.html` は実測を差し込むための空き地）。
書き出しはデコードもエンコードも WebCodecs なので Node 側に測る相手が無く、
ブラウザを使うが人は触らない、という形になっている。
`project-pack` も**触る画面を持たない**。測る相手が「ファイルのバイト列」なので
Node だけで全部測れる（ブラウザも素材も要らない）。本体へ入れるときに
`SettingsPage` の保存／開くへ繋ぐ話になるので、画面はその回で作る。
`keyframe` の画面は 2026-09-27 の 2 回目に入った（打点を置く・つまむ・繋ぎ方を選ぶ）。
**この試作は素材を読まない**——打点は秒と値しか見ないので、絵は `<video>` / `<img>` に
そのまま出させるだけで足り、コマの列に起こす必要が無い。

`lab:test` は**すべての試作の検算をまとめて走らせる**（1 つだけ緑にして終わらないため）。
`lab:uitest` も同じで、**画面を持っている試作ぜんぶ**（`auto-cut`・`beat`・`scene-cut`・`thumbnail`・
`reframe`・`keyframe`）を続けて通します（`export-cost` と `project-pack` は触る画面が無いので
入っていません）。

確かめ方は 4 段に分けてあります。役割が違うので、どれか 1 つで済ませないでください。

| | 何を見るか | いつ使うか |
| --- | --- | --- |
| `lab:test` | 計算が合っているか | 手を入れるたび。数秒で終わる |
| `lab:probe` | どの手なら見分けられるか | 新しい判定を考えるとき。**実装する前に** |
| `lab:bench` | 実際どれくらい効くか | 効きに関わる変更をしたとき。**数字を記録に残す** |
| `lab:uitest` | 読み込む → 描く → 鳴らす、が繋がっているか | 画面に手を入れたとき |

`lab:loudness` と `lab:clipmatch` はこの 4 段とは別の軸です。上の 4 つが「どこを切るか」を
見るのに対して、あちらは「どれくらいの大きさで出すか」を見ます。
**2 つの役割は違います**: `lab:loudness` は**タイムライン全体**を目標へ合わせる話
（ラウドネス正規化とリミッタ）、`lab:clipmatch` は**その中のクリップどうし**を揃える話です。
順番は「クリップごとに揃える → 繋ぐ → 全体を目標へ → 均す」で、逆にすると
全体の倍率をクリップごとのばらつきが決めてしまいます（2026-09-20・2 回目）。
**リミッタの前後を並べたいときは `LAB_LIMIT=0` を付けたものと突き合わせてください**
（付けると 2026-09-19 までの「倍率ひとつだけ」の形に戻ります）。

**ラウドネスの側も、数字を 1 つで読まないでください。** 目標へ揃ったかだけを見ると、
山を潰して揃えた場合と区別が付きません。`lab:loudness` は「均した深さ」と
「均していた時間の割合」を併せて出します。そこが伸びているなら、
揃えたのではなく小さくしただけかもしれません（2026-09-20）。

**クリップを揃えたかどうかも、クリップの開きで読まないでください。** 測った値を引き算すれば
必ず縮むので、そこは何も言っていません。`lab:clipmatch` は `spec.mjs` の発話区間の正解で
**「声が揃ったか」を測り直して**出します（2026-09-20・2 回目）。

**声の無い素材の「削減 X%」を、そのまま実害として読まないでください。**
素材にもともと開いている無音を切っただけなら、曲は壊れていません。
`lab:bench` と `lab:probe` は「そのうち何秒が**鳴っているところ**だったか」を併せて出します。
そこがゼロなら実害はありません（2026-09-14・3 回目に、ここを読み違えていたことが分かりました）。

**拍の素材も、正解の「拍の秒の並び」のほうが本体です。** BPM だけを正解にすると、
テンポは当たっているのに拍が裏に乗っている手を「当たり」と数えてしまいます。
`lab:beat` は「BPM の当たり」と「拍の F 値」を必ず併せて出します（2026-09-21）。

**「拍は無い」と言えるかも併せて見てください。** 拍の無い素材に何かを答えてしまう手は、
曲に合わせてカットを置く機能としては使えません。
なお**その線は尺で動きます**——短い素材では雑音でも高い山が立つので、
固定値では引けません（`beat/src/tempo.ts` の `minClarity` の表）。

**映像の素材はファイルに書き出していません。** 1 本 7MB あり、本物の動画にするには
エンコーダが要るためです（外部ライブラリを足さない方針）。種を固定した生成なら
毎回 1 ビットまで同じものが出るので、数字を並べる目的はそれで満たせます。
中身と正解は [`fixtures/scenes.mjs`](./fixtures/scenes.mjs)、作るのは `make-frames.mjs` です。

音の素材は**種を固定して生成**しています。毎回まったく同じ音が出るので、
「昨日は 37% 削れた／今日は 41% 削れた」をそのまま比べられます。
どこでしゃべっているかも `lab/fixtures/spec.mjs` に書いてあるので、正解と突き合わせられます。

素材には**わざと意地悪なもの**（`※` 付き）が混ぜてあります。自分の手を潰しにいく素材が無いと、
「うまくいった」の中身が「自分に都合のいい素材で試しただけ」になります。
新しい判定を入れるときは、それを潰す素材も一緒に足してください。

実際、2026-09-10 に足した `music-tremolo.wav`（声と同じ速さで震える楽器だけ）は、
その日に入れようとしていた判定を**その場で壊しました**。壊れることが分かったから作り直せたので、
あの素材が無ければ「うまくいった」と書いて終わっていたはずです。

2026-09-11 の `music-wah.wav`（声と同じ速さでフォルマントが動く楽器だけ）も同じです。
その日に入れようとしていた「包絡の動きで声を見分ける」手を潰しました。
ただし**この素材の読み方は 2026-09-14（3 回目）に間違いだと分かりました。**
「声がゼロの素材を 7 本に切り刻む」と書いていたのは、7 本に分かれる原因が
この素材自身に開いた 5.32 秒の無音だったためで、**鳴っているところは 1 コマも切っていません**。
判定はいまも誤認していますが、実害は出ていませんでした。

2026-09-13 の `music-hats.wav`（和音の上でハイハットが刻む音楽・声なし）は、
**`music-chords.wav` とハイハットの有無だけ**が違います（和音も背景も乱数の種も同じ）。
ハイハットを足しただけで、声らしいコマの割合が 33% → **88%**、形が動いた秒数が
0.04 → **12.98 秒**（13 秒中）になり、**4 つの判定すべてを素通り**しました。
同じ日の `music-flute.wav`（息の雑音を持つ管楽器・声なし）も同じように素通りし、
さらに削減 7%（声がゼロなのに切った）という実害まで出ました。

この 2 本を足した理由は、**「雑音の粒があるか」で声を見分ける手を、手元の素材では
そもそも検証できなかった**からです。音楽の素材 6 本のうち 5 本が正弦波の和で、
雑音を持つのは打楽器 1 本だけでした。**分ける側に雑音が無い状態で「雑音があれば声」を測れば、
必ず良い数字が出ます。** それは判定の出来ではなく、素材の偏りを測っているだけです。

2026-09-13（2 回目）に足した 3 本は、**その日に自分で考えた手がかりを潰すために作ったもの**です。
「打点は重心が単調に下がり続ける／口の動きは向きがばらばら」という手（`centroidDescent`）は、
`music-hats.wav` の 97% を弾くのに対し `speech-hats.wav`（**同じハイハットの上でしゃべる。
声は `speech.wav` と 1 ビットも同じ**）は 29% しか弾かず、いかにも効きそうに見えました。
そこへ残りの 2 本を足したら終わりました:

| 素材 | 何が違うか | 結果 |
| --- | --- | --- |
| `speech-hats.wav` | `speech.wav` ＋ ハイハット | 声のコマの **29%**（通る） |
| `speech-vowels-hats.wav` | `speech-vowels-only.wav` ＋ ハイハット | 声のコマの **83%**（破れる） |
| `speech-sparse-hats.wav` | `speech-sparse-bgm.wav` ＋ ハイハット | 素材全体の **99%**（破れる） |

3 本とも**ハイハットを足しただけ**で、ほかの音は 1 ビットも変わりません
（そのためにハイハットを生成の最後へ移しました）。だから「何が効いたか」に推測の余地がありません。
分かったのは、その手が見ていたのは「口が動いたか」ではなく
**「声が高い帯域を覆えているか」**だったということです。ハミングや伸ばした母音は覆えないので、
伴奏の上でそれをやると声ごと打点に見えます。

2026-09-13（3 回目）の `speech-sustained-hats.wav`（ハイハットの上で母音を長く伸ばす声）は、
**その日に作った判定を、入れる直前に潰した素材**です。「低い帯域が動かないまま高い帯域だけが
動いたコマは打点だ」という門は、24 本のうち 23 本で**何も失わずに**効いていました
（`music-hats` の削減 0% → 35%、`speech-sparse-hats` の精度 20% → 23%、取りこぼしはどこも増えず）。
そこで「低い帯域が動かない声」＝伸ばした母音を、同じハイハットの上に置いた 1 本を足したところ、
声のコマの中央値が **0.571** と `music-hats`（0.571）に並び、声を残せた率が 100% → **73%** に落ちました。
**24 本目が無ければ、そのまま入れていた**判定です。

2026-09-14 の `music-vibrato.wav`（音程が声と同じように動く楽器・声なし）は、
**手元の音楽の偏りを埋めるために足した**ものです。それまでの音楽は、音程が完全に固定か
（`bgm`・`music-tremolo`・`music-wah`）、階段状に跳ぶか（`music-chords*`）、
音程が無いか（`drums`・`hats`）のどれかしかありませんでした。
**音程が滑らかに動く音楽が 1 本も無い状態で「音程が動けば声」を測れば、必ず良い数字が出ます。**
`music-flute.wav` を足した理由とまったく同じ構図です。

動かし方は声に合わせてあります。ビブラートは合成の声の抑揚と**同じ ±4%・1.7Hz**、
音と音の間はポルタメント（0.09 秒）で渡ります。**声と違うのは共鳴が固定であることだけ**なので、
破れたときに何が効いたのかに推測の余地がありません。

足したその場で **4 つの判定すべてを素通りし**、声がゼロなのに 4% 削りました。
ところが**破っていたのはビブラートではありませんでした**。音程の揺れ（±4% ≒ 5Hz）は
いちばん狭いメル帯域（約 80Hz）の中に収まるので、包絡はほとんど動きません（中央値 0.020）。
動かしていたのは**音の変わり目**だけで、そこを均しと保持が引き伸ばしていました。
**素材を作らなければ「ビブラートで破れた」と書いて終わっていた**はずです。

2026-09-14（2 回目）の 2 本は、**「捨てた量を置き場所を変えて測り直す」手を潰すため**に足しました。

| 素材 | 何が違うか | 何のために |
| --- | --- | --- |
| `speech-sparse-sustained-hats.wav` | `speech-sparse-hats.wav` の声を伸ばした母音に替えただけ | 声が薄い素材で、素材単位の判定にどれだけ余裕があるかを見る |
| `music-hats-break.wav` | `music-hats.wav` の和音を 2 回休ませただけ | **削減 0% が「守れている」のか「まだ撃たれていない」のか**を切り分ける |

2 本目の役割が、この日のいちばんの収穫でした。`music-hats.wav` は声らしいコマの割合 99%・
形が動いた 13.0 秒で**素材単位の判定を 2 つとも素通りしている**のに、削減は 0% です。
止めているのは判定ではなく、**13 秒ずっと同じ大きさで鳴っているという素材の側の事情**でした。
和音を 2 回休ませる（現実の曲のブレイク）だけで 3% 削り始めます。
**表の 0% を「守れている」と読むと、守れていないものを守れていると数えます。**

1 本目は、前の回に書いた「素材単位の判定は 2〜3 割取りこぼしても結論が変わらない」を潰しました。
その余裕は**声がたっぷり入っている素材にしか無く**、声が 2 割しか無い素材では
同じ取りこぼし率でそのまま「声が見つからない」に落ちます（詳しくは `auto-cut/README.md`）。

**意地悪なのは「声でない素材」だけではありません。** 2026-09-11（2 回目）に足した
`speech-sustained.wav`（母音を長く伸ばす声）は、まぎれもない声なのに包絡が動きません。
その日に開こうとしていたコマ単位の門を、作ったその場で潰しました（声の 6 割を切る）。
**判定を通ってほしいのに通らない素材**も、同じだけ価値があります。

2026-09-12 の `music-chords-faster.wav`（和音が 0.2 秒ごとに変わる音楽・声なし）は、
**前の回に「破れるはず」と書いて残しておいた素材**です。実際に破れました。
0.4 秒ごとの `music-chords-fast.wav` と**和音の間隔しか違わない**のに、片方は止まり、
片方は 4 つの判定すべてを素通りします。ほかを変えずに 1 つだけ変えた 2 本を並べると、
**判定が本当は何を見ていたのか**が出ます（この場合は「声かどうか」ではなく「変化の間隔」）。

### 合成の声について（2026-09-11・2 回目に作り直した）

`speak()` はもともと、倍音を 4 本重ねて音量を 4.2Hz の正弦波で揺らすだけのものでした。
**発話中ずっと倍音の重みも音程も変わらない**ので、スペクトルの上では
「トレモロのかかった楽器」とまったく同じものだったことになります。
そのせいで、包絡の動きを使う判定も、揺れの規則正しさを使う判定も、
**素材のほうが先に破れて試せない**という詰まりが起きていました。

いまは倍音列に母音の共鳴（3 つのフォルマント）を掛け、音節ごとに母音を選び直し、
音節の長さを振り、抑揚で基本周波数を動かしています。
**測った数字がおかしいときは、判定より先に素材を疑ってください。**
作り直したときに実際、過去の結論が 2 つ成り立たなくなりました（詳しくは JOURNAL の同日）。

平板だった頃の声は `makeShort` に `{ flat: true }` を渡せば作れます（乱数の消費数まで
当時と同じなので、同じ種なら 1 ビットも変わりません）。過去の数字を測り直すためのものです。

### 子音と息について（2026-09-12・2 回目に足した）

上の作り直しでも、声は**母音だけ**でした。子音も息の雑音も無いので、
**広い帯域に散る雑音の粒がまったく入っていません**。
手で考えた手がかりが 5 つとも自作の楽器の素材に負けたあとで記録を読み直すと、
破れた 5 つはどれも「音程・包絡・揺れ」しか見ていませんでした。
**本物の話し声が楽器と決定的に違うのはそこ**なので、
いちばん効きそうな手がかりを、素材が表現できないせいで一度も試せていなかったことになります。

いまは音節の頭に摩擦音（`s`・`sh`・`f`）か破裂音（`t`・`k`・`p`）を置き、
母音を鳴らしている間は薄い息の雑音を重ねています。6 つに 1 つは母音で始まります
（必ず頭に雑音がある声は、現実より都合がよすぎる）。

足したあとで測ると、**判定側の結論が 2 つ動きました**（数字は JOURNAL の同日）:

- `speech-sustained`（母音を伸ばす声）の**取りこぼしが 0% から 25% に増えた**。
  原因は息ではなく子音で、`modulation`（音節の速さ）が落ちたため。
- `tone`（音色の尖り具合）が、BGM の乗った素材で**逆向きになった**。
  本物の声は正弦波の和音より雑音的なので、息を足すと音楽のほうが「尖って」見える。
  声らしさの片方が成り立っていたのは、**雑音の無い合成音のおかげ**でした。

子音も息も無い声は `{ vowelsOnly: true }` で作れます（同じ種なら足す前と 1 ビットも変わりません）。
これは過去の数字を測り直すためだけのものではなく、
**`speech-vowels-only.wav` として一覧にも置いてあります**。ハミング・詠唱・歌の母音のように、
子音がほとんど無い発声は現実にあるので、子音に頼る判定を入れるなら
**それがこの素材を切らないこと**を必ず併せて見てください。

2026-09-15 の `speech-chord-into.wav`（和音が鳴り止んだ瞬間にしゃべり出す。声あり）は、
**その日に入れた「発話の頭を遡って拾う」手を潰すために作った**ものです。
遡りは鳴っているあいだだけ戻るので、損をするのは「声の直前まで、声でない音が鳴り続けている」ときだけ。
`speech.wav` にその形だけを足してあります（声は 1 ビットも同じ）。

**最初は減衰する一撃（スティンガー）で作って、潰す先に届きませんでした。**
打点は声らしさの判定を素通りするので、**遡りが無くても丸ごと残ります**。
遡りの有無で数字が 1 ポイントも動かず、punisher になりませんでした。
持続する和音に替えたら効くようになり（精度 66% → 64%）、そこで初めて代価が測れました。
**潰す素材は「判定が確かに弾く音」で作らないと、潰したいものに届きません。**
「意地悪そうに見えるか」ではなく「いま入れた手が、それで本当に損をするか」で選ぶこと。

2026-09-16 の `speech-sparse-thump.wav`（**ハイハットと同じ刻みを 700Hz より下へ寄せただけ**の打点。
声あり）は、**その日に考えた「揺れを低い帯域だけで見る」手を、入れる前に潰すため**に作りました。

あの手は `speech-sparse-hats` の切れ目 5.60 秒を渡らせないために考えたもので、実際に渡らなくなります
（削減 0% → 64%）。ただし効いた理由ははっきりしていて、**ハイハットが 6kHz より上にしか居ないから**です。
低い側だけを見れば、あの素材は `speech-sparse-bgm` と 1 ビットも違わなくなります。

だとすれば、**同じ刻みを低い側へ置けば、乗っているものがそのまま外れる**はずです。
そのために刻みの速さも減衰も引く乱数もそのままにして、寄せる高さだけを入れ替えました
（`hats` と `thumps` を同じ `pulses` から作り直してあります）。差は**打点がどの帯域に居るか**だけです。

結果は、切れ目の 99% が 0.2 を超えたまま渡り切る——**入れる前と 1 コマも変わりません**。
この素材が無ければ「声を見分けられるようになった」と書いていたはずですが、
見分けているのではなく、**邪魔なものがたまたま声の帯域の外に居ただけ**でした。
タムやキックで刻む伴奏は現実にいくらでもあるので、意地悪というより外せない素材に近いものです。

2026-09-16（3 回目）の `speech-clipped-bgm.wav`（BGM の上で、**短く区切って**たまにしゃべる。声あり）は、
**その日に考えた「低い側の音量が下に張り付いてたまに跳ねるのは打点」という手を潰すため**に作りました。

あの手は、打点と音節で**デューティ比が逆を向いている**ことに乗っています。
打点は鳴っていない時間のほうが長く、音節は鳴っている時間のほうが長い。
実際 `speech-sparse-thump.wav` では、同じ素材の中で声のコマ（歪度の中央値 -0.11）と
打点だけのコマ（+0.77）が**重なりなく割れました**。9/13 から 8 通り試して 1 コマも動かなかった穴です。

だとすれば、**鳴っていない時間のほうが長い声**を置けばそのまま外れるはずです。
`speech-sparse-bgm.wav` と**しゃべり方だけ**を変えました（BGM も種も同じ。乱数は音節を
組み終わったあとの包絡にしか効かないので、音節の並びも母音も子音も 1 ビット同じ）。

結果は歪度の中央値 **1.34**——**打点（0.74）よりも高い**。門を入れると、この素材は
声らしいコマの割合が 25% → 2% まで落ちて「声が見つからない」で止まります
（削減 64% → **0%**）。声を切りはしませんが、その話し方では道具が働かなくなります。

**あの手が見ていたのは「打点か」ではなく「鳴っている時間と黙っている時間のどちらが長いか」**でした。
きっぱり区切ってしゃべる（カウント・呼びかけ・区切ったナレーション）は珍しくないので、
この素材が無ければ「声の帯域の打点を見分けられた」と書いて終わっていたはずです。

2026-09-17（3 回目）の `music-thump-drop.wav`（**うねらない伴奏の上で低い打点が刻み、
打点だけが 2 秒落ちる**音楽・声なし）は、**同じ日の 2 回目に入れた「向きの門を素材ごとに外す手」
（`skewDropped`）を潰すため**に作りました。

あの手の根拠は「門が触れないコマの割合（下限）が 5% の線より上だから、
この門で素材単位に止まるのは声のある素材だけ」——つまり
**門が立てる「声が見つからない」は構造上どれも誤り**、という読みでした。
実際、当時の 33 本で外れるのは `speech-clipped-bgm`（声あり）1 本だけです。

ところが**下限は「窓 ÷ 尺」でしかありません**。低い側が全編鳴っていれば、
読めないのは窓の幅ちょうど（31 コマ）で、声の有無とは何の関係もありません。
13 秒なら 4.6% で、線のすぐ下です。だとすれば、
**低い側がへこまない声ゼロの素材**を置けばそのまま線を割るはずです。

前の回は「和音を厚くすると向きが下がる」ので作れないと書いていましたが、
**要るのは厚さではなく、低い側がへこまないこと**でした。
うねり（`bgmSwellDepth`）を 0 にして伴奏を一定にするだけで届きます。
`speech-sparse-thump.wav` の背景から声を抜き、打点だけが落ちる区間（`thumpBreaks`）を
2 つ置いてあります。**落ちサビでドラムだけが抜ける形**で、曲としてはありふれたものです。

結果は、門が**読めるコマを 1 つ残らず捕まえて**正しく止めるのに、外し方がその結論を捨て、
声がゼロの曲を 1.60 秒切ります。**外し方が働くのは、門がいちばんよく効いたときでした。**
しかも下限は尺に反比例するので、**同じ素材を 5 回つなぐ（65 秒）と実害は 8.00 秒**に伸びます。
この素材が無ければ「声のある素材が壊れる件は塞いだ」と書いたまま次へ行っていたはずです。

**ついでに既定の判定も撃たれました。** この素材は門と関係なく 1.60 秒切ります
（声がゼロなのに鳴っているところを切る素材は、これが初めてです）。
切れ目は**打点が落ちている区間の中**にあり、伴奏が鳴り続けていても
刻みが止まると声らしさが落ちます。詳しくは `auto-cut/README.md`。


2026-09-18 の `speech-flat-bgm.wav` / `speech-flat-bgm-loud.wav`（**うねらない伴奏の上でしゃべる**。
声あり）は、**その日に考えた「深さ（dB）の線を上げて `music-thump-drop` を止める」手を、
入れる前に潰すため**に作りました。

`music-thump-drop`（声ゼロ）の深さは 1.01dB で、**当時の線 0.8 と
「守りたい下限」だった `speech-bgm-loud` の 1.59dB のちょうど間**に居ます。
線を 1.26 あたりへ上げれば止まる——ように見えました。

だとすれば、**声があるのに深さが 1.01 と 1.26 の間に来る素材**を置けば外れるはずです。
深さは**音量（dB）の列の揺れ幅**なので、線形に直せば「窓の中の最大と最小の比」でしかなく、
**一定の伴奏を下に敷けば縮む**からです。`speech-bgm-loud.wav` から
**伴奏のうねりを外すだけ**（音量も種も同じ。声は 1 ビット同じ）で作れます。

結果は **1.09dB**——狙いどおり間に落ちました。線は上げられません。
**ついでに、下げるべきだったことも分かりました。** 伴奏をもう一段上げた
`speech-flat-bgm-loud`（0.69dB）は**当時の線 0.8 を割って**、声があるのに素材ごと止まります。
つまりこの穴は今回開いたのではなく、**前からあって素材が無かっただけ**です。
1.59dB を「守りたい下限」と読めていたのは、**その素材の伴奏がたまたまうねっていたから**でした。

伴奏を上げ続けると声の側は下がり続け、**声より 7.6dB 大きいところで
声ゼロの `music-chords-faster`（0.361dB）を下回ります**。群が並んでいるのではなく、
**線が 1 本の連なりの真ん中を通っています。** 線は 0.8 → 0.5 へ下げましたが、
それは「どこまでの伴奏を守るか」の宣言でしかありません。

**2026-09-16（2 回目）に「割合は揺れの大きさを捨てた比だった」と直した先も、比でした。**
捨てるものが「揺れの大きさ」から「伴奏の大きさ」へ移っただけです。
そのとき自分で書いた戒め（**いま使っている量が「比」になっていないかを疑うこと**）は、
**その回に入れた量そのものに当たっていました。**

2026-09-19 の `speech-bgm-fade.wav`（**伴奏がフェードアウトしていく上でしゃべる**。声あり）は、
その日に入れた**低い側の線の置き方**を潰すために足しました。

線は「低い側が鳴っているか」を決めるもので、それまで**全域と同じ自動しきい値**を当てていました。
そのせいで低い側が大きい素材ほど読めなくなる（打点を 2 倍にすると 12.38s → 0.04s）ので、
線を**低い側の大きさ**から取るように直しました。だとすれば、
**素材の中で低い側の大きさが動けば外れる**はずです。

基準を素材ぜんたい（p90）で取ると、大きかった頃の値が小さくなった側にも残るので、
後半が丸ごと「鳴っていない」になります。`speech-flat-bgm.wav` と
**伴奏がフェードするかどうかだけ**が違います（音量も種も同じ 0.4 / 6）。
段差ではなく 13 秒で連続に 24dB 下げてあるので、**縁（曲の切れ目）の話と混ざりません。**

実際 14dB 幅では、後半の読めた秒が **1.18s** と全域の線（2.12s）より減りました。
そこで基準を**その場（前後 2.5 秒）の最大**に取る形へ変えてあります。
**ナレーションの下で BGM がフェードする・ダッキングする**のはごく普通の形なので、
意地悪というより外せない素材に近いものです。

### 映像の素材について（2026-09-20・4 回目に作った）

シーン検出の側も同じ作り方です。**自分がその日に選んだ手を、裏返して潰す素材**を
一緒に足しています。

`cuts-samebright`（明るさの分布はそのまま、色だけが変わるカット・正解 2 本）は、
その日に既定として選んだ量（明るさの分布）を潰すために作りました。
選んだ理由は「画面の中で物が動いても分布は動かないからパンに強い」でしたが、
だとすれば**明るさを動かさないカットは原理的に見えない**はずです。
実際 0.011 しか動かず（色の分布なら 0.886）、2 本とも見逃しました。
**選んだ理由をそのまま裏返すと、潰す素材の作り方になります。**

`quick-insert`（0.33 秒の短いインサートが 2 回挟まる・正解 4 本）は、
フラッシュを落とすために入れた門（前後を 6 コマまたいで比べる）を潰すために作りました。
またぐ幅より短い場面は、門が**丸ごとまたいで**前後に同じ絵を見つけてしまいます。
候補は 4 本とも立つのに、門が 4 本とも落としました。
**同じ 0.4 秒という幅が、片方ではフラッシュを落とし、もう片方では本物のカットを落とします。**

`pan-reveal`（カメラが流れ続け、新しい景色が入ってくる）は、**素材の側の甘さ**を潰しました。
最初に作った `pan` は帯が巡る作りで、画面から出ていった中身が逆側から戻ってきます。
**出入りする中身が同じなら、分布は原理的に 1 ビットも動きません。**
つまりあの素材の上で「分布はパンに強い」と測っても、手の性質ではなく素材の性質を測っています。
一度も戻らない帯に替えたところ、誤検出の上限が 0.006 → **0.051** に上がり、
線の余裕が 4.8 倍から 3.3 倍へ縮みました。空振りは増えませんでしたが、
**「強い」の中身が変わりました**（詳しくは `scene-cut/README.md`）。

**映像の側では、正解の置き方そのものが間違っていた例も出ました。**
黒へ落ちて黒から上がるフェードの正解を、最初は「渡り切る真ん中」の 1 点に置いていました。
測ったら検出は黒の**両端**を正しく見つけていて、真ん中では何も起きていません。
黒が 1 秒続くあいだ絵は動かないので、そこには止まっている区間が 1 つあり、切り所は 2 つあります。
**正解が外れたときは、判定と素材だけでなく正解の置き方も疑ってください。**
