# ラボを 1 回ぶん進める

`lab/` を 1 回ぶん前へ進めてください。日本語で作業し、日本語で報告してください。

この手順は 1 日 3 回（9 時 / 12 時 / 17 時）走ります。**1 回で 1 テーマ**です。
前の回の続きになることが多いので、記録の読み方は下の「最初にやること」のとおりに。

**トークンは気にしなくて構いません。** 急いで済ませるより、調べる・測る・確かめるところに使ってください。
半端な実装を 3 つ置いていくより、ひとつのテーマを最後まで詰めるほうが価値があります。

## リポジトリ

- 作業ディレクトリ: `/home/user/vivid-edit`
- リポジトリ: `https://github.com/Oz-k17/vivid-edit`、ブランチは `main`
- `node_modules` が無ければ先に `npm install` してください。

2026-09-28 まで、作業は `discord-calendar-bot` の作業ブランチで進め、あとから
こちらへ移していました。**移す間に配り先が古いままになる**ことが起きたので、
いまは製品のリポジトリ 1 つに直接置いています。NAS へ配る compose も、ここを見ています。

### push できるかを、作業を始める前に確かめる

自動起動のセッションは、リポジトリを**読めても push できないことがあります**
（git プロキシが押し先の無いセッションを弾く）。これに気づかないまま進めると、
20 分かけた作業が最後に丸ごと消えます。実際に 2026-09-08〜09-10 の自動実行 3 回ぶんが
そうやって失われました。

なので **いちばん最初に**、空でよいので push が通ることを確かめてください:

```
cd /home/user/vivid-edit
git fetch origin main && git status
git push --dry-run origin HEAD:main
```

`--dry-run` が **通らなかったら、そこで作業を始めないでください。**
何を作っても残らないので、時間の無駄になります。代わりに、

- エラー文をそのまま添えて、**「push できないので今回は作業していません」と報告して終わる。**

これが正しい終わり方です。黙って作業を進めて消すより、ずっと役に立ちます。

## 最初にやること（必ず）

1. `lab/JOURNAL.md` を読む。**セッションは毎回まっさらな状態で始まるので、ここに書いてあることが唯一の引き継ぎです。** 特に過去の「分かったこと」と「積み残し」。
2. `lab/README.md` と、触る試作の `README.md` を読む。
3. 触る予定のコードを、ざっとではなく**きちんと読む**。本体（`src/`）に繋がる話なら、その接続先（`src/engine/` `src/model/`）も読んで、どこに乗るのかを掴んでから設計する。
4. `npm run lab:test` を走らせ、いまが緑であることを確かめる（赤ければ、その修復が今回の作業）。

## 今回の作業

`lab/JOURNAL.md` の「やることの候補」から、**いまいちばん効きそうなテーマを 1 つ**選んでください。
直前の回に積み残しがあるなら、まずそれを見てください。
候補になくても、記録を読んで「これが要る」と判断したものがあればそちらを優先して構いません
（その場合は候補にも追記する）。

### 完璧を求めない。ある程度使えるようになったら次の項目へ

**いまの出来で十分だという判断は、すでに人が出しています**（2026-09-19）。
声の自動カットは **声を残せた率 99% 以上・残したうち声だった率 70% 以上**を満たしていれば
「使える」と見なしてよく、そこから先の 1〜2 ポイントを追うより、
**まだ手を付けていない項目を 1 つ動くところまで持っていくほうが価値があります。**

- **同じ穴に 2 回続けて挑んで数字が動かなかったら、そのテーマは凍結して別の項目へ移る。**
  「あと 1 つ手が残っている」は、たいてい 3 回目も残ります。
- **候補のうち、まだ一度も触っていない項目を優先する**（「やることの候補」で取り消し線も
  日付も付いていないもの）。音まわりだけでなく、映像・書き出しの側も同じ列に並んでいます。
- 凍結したテーマを開け直すのは、**別の場所を直した副作用で状況が変わったときだけ**。
  実際そういう例はあります（`speech-sustained` の取りこぼしは、3 回「つまみでは直せない」と
  書いたあと、低い帯域の見方を直したら消えました）。自分から掘り返しにいかないこと。
- ただし**上の線を下回る変更は、精度の追求ではなく不具合**です。そこは直してください。

進め方:

- **テーマは 1 つ。ただし、その 1 つは深くやる。** 実装だけで終わらせず、検算を足し、実際の素材で測り、必要なら画面から触れるようにし、README に「なぜそうしたか」を書くところまでを 1 セットとします。
- **まず測ってから設計する。** 「効きが悪い」と思ったら、直す前にいまの数字を出してください（`npm run lab:bench`）。前後の数字が並んで初めて、良くなったと言えます。
- **自分の手を潰す素材を先に作る。** 新しい判定を入れるなら、それが破れる素材も一緒に足してください。
  意地悪な素材が無いと、「うまくいった」の中身が「自分に都合のいい素材で試しただけ」になります。
- **やってみて筋が悪いと分かったら、無理に完成させず引き返す。** その場合は「何を試して、なぜ駄目だったか」を記録に残してください。**それも立派な 1 回ぶんの成果です。** 次の回の自分が同じ穴を掘らずに済みます。
- 迷ったら、**動くところまで持っていけるほうへ範囲を削って**ください。中途半端に大きいものを残さない。

守ること:

- **`lab/` の中だけを触る。`src/` `docs/` `ios/` には手を出さない。** 本体へ入れるのは別の機会に、人が判断して行います（読むのは自由です、むしろ読んでください）。
- **判断する部分は DOM にも WebAudio にも依存させない。** そうしておけば Node が `.ts` をそのまま実行できるので、テストがブラウザ無しで回ります。画面（デモ）と計算は必ず分けてください。
- **新しく書いた判断ロジックには、合成データでの検算を必ず足す。**
- 外部ライブラリを足すのは避けてください。どうしても要るときは、記録に理由を書いてください。
- コメントと文章は、既存のコードと同じ調子で日本語で。「何をしているか」ではなく「なぜそうしたか」を書いてください。

## 確かめ方（4 段。役割が違うので、どれか 1 つで済ませない）

| | 何を見るか |
| --- | --- |
| `npm run lab:test` | 計算が合っているか（合成波形・ブラウザ不要・数秒） |
| `npm run lab:probe` | どの手なら見分けられるか（正解付き。**実装する前に**） |
| `npm run lab:bench` | 実際どれくらい効くか（**数字を記録に残す**） |
| `npm run lab:uitest` | 読み込む → 描く → 鳴らす、が繋がっているか |

素材は `npm run lab:fixtures` で作れます。種を固定してあるので、前後の数字がそのまま比べられます。

**削減率だけを見ないこと。** 全部削れば 100% になりますが、それは声ごと消しているだけです。
`lab:bench` が出す「声を残せた率 / 残したうち声だった率」を必ず併せて見てください。

push する前に、自分の差分を**粗探しするつもりで読み直して**ください。
境界値、素材が空のとき、値が極端なとき。気づいた穴はその場で塞ぐか、塞げないなら記録に書く。

## 終わったら（必ず）

1. `npm run lab:test` / `npm run lab:typecheck` / `npm run lab:uitest` が緑であることを確認する。
2. `npm run build`（本体）も通ることを確認する。ラボは切り離してありますが、壊していないことの確認です。
3. `lab/JOURNAL.md` の「記録」のいちばん上にその日の日付で追記する。書くのは:
   - やったこと（3 行以内）
   - **測った数字**（効きに関わる変更をしたなら、前後を並べて）
   - **やってみて分かったこと・うまくいかなかったこと**（必ず 1 行以上。次の回の自分にとっていちばん価値があるのはここです）
   - 積み残し（あれば）
4. commit して `origin` の `main` へ push する。押し先はここ 1 つです。
   通らなければ、その回の成果は残りません。
5. 何をやって、何が分かって、次に何をやるとよさそうかを、日本語で短く報告する。
   **`origin` への push が通らなかったときは、報告の 1 行目に必ず
   「push できていません」と書いてください。** ここを濁されると、
   何日も失敗に気づけません（実際に 3 日気づけませんでした）。

うまく進まなかった回は、それも正直に記録して push してください。
「これを試したが駄目だった」という記録も、次の回の判断材料になります。

## 同じ日に 2 回以上呼ばれたとき

通常どおりです（1 日 3 回が既定なので、たいていはこちらになります）。
記録の見出しは `### 2026-09-07（2 回目）` のように回数を添えてください。
前の回の「積み残し」がそのまま次の回の第一候補になります。

同じ日のうちは、**前の回で触ったところを続けて深めるほうを優先**してください。
1 日に 3 つの別テーマを浅く置いていくより、そのほうが残るものが大きくなります。
